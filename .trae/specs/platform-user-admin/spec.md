# 平台端用户管理增强 — 需求说明

> 状态：**已批准（已实现）**
> 创建：2026-11-19
> 仓库：Smartorder（campus food-order 全栈）

---

## 1. 问题与用户

### 问题
控制台「用户管理」页（`/platform/users`）目前只有 **列表 / 详情 / 封禁 / 解禁** 三类能力：

| 能力 | 现状 |
|---|---|
| 学籍认证审核 | ❌ 缺失。`u_user.verify_status=1`（待审核）用户只能看到「审核中」标签，没有任何通过/驳回按钮 |
| 用户资料修改 | ❌ 缺失。手机号、学院、校区、宿舍楼、学号等字段只能在 DB 里改 |
| 删除用户 | ❌ 缺失 |

同时学生注册（学号密码注册）后 `verify_status` 固定为 1（待审核），注册流程不采集手机号/学院/校区，学生端也没有资料编辑入口，导致这批用户长期处于「信息不全 + 永远审核中」的状态。

### 用户
- 平台管理员（PLATFORM_ADMIN）：控制台用户管理页的操作者
- 学生用户：被审核、被编辑资料的對象

### 非目标
- 不做学生端自助修改资料（H5 个人资料编辑）——本次通过平台代改覆盖该诉求，后续可复用同一套校验逻辑再做学生端
- 不做批量操作（批量审核/批量删除）
- 不做学生认证材料上传/证件照审核（`u_verify_apply` 表当前未启用，本次不接入）
- 不改动登录、封禁、订单等既有逻辑

## 2. 目标

### 2.1 认证审核
1. 用户列表中 `verifyStatus=1` 的行展示 **通过 / 驳回** 按钮；`verifyStatus=3` 展示 **重新通过**。
2. 「通过」：`verify_status → 2`，可填写备注（选填，≤255 字），提交后 toast 并刷新列表。
3. 「驳回」：`verify_status → 3`，必须填写驳回原因（≤255 字）。
4. 审核使用 `expectedVerifyStatus` 做并发保护（先读后写，状态被其他管理员改过时提示刷新重试）。
5. 驳回原因写入 `u_user.verify_note`，控制台详情可见；学生端个人页在「认证被拒」时也展示该原因。

### 2.2 用户资料修改
1. 行操作与详情弹窗提供「编辑资料」入口，弹窗表单字段：
   - 昵称（≤64）、真实姓名（≤32）、学号、手机号、学院（≤64）、校区（≤64）、宿舍楼（≤64）
2. 校验：
   - 手机号：空 或 11 位大陆手机号（`^1[3-9]\d{9}$`），全局唯一（`uk_u_user_phone`）
   - 学号：空 或 4–32 位字母数字（兼容演示账号 `admin`），全局唯一（`uk_u_user_student_no`）
   - 其余字段按 DB 长度截断校验，提交前 trim
3. 手机号/学号清空时写 `NULL`（保留唯一索引对多 NULL 的兼容）。
4. 唯一冲突返回明确文案（「手机号已被其他用户使用」/「学号已被其他用户使用」），不暴露 SQL。
5. 保存成功后刷新该行数据，不整页 reload。

### 2.3 删除用户
1. 行操作与详情弹窗提供「删除用户」，二次确认弹窗明确提示「不可恢复，将清除地址、收藏、优惠券、购物车、通知等个人数据」。
2. 删除前校验：该用户在 `o_order` 中存在订单记录时 **拒绝删除**，提示「该用户存在订单记录，为保证对账请改用封禁」。
3. 允许删除时执行物理删除，依赖既有外键：
   - `u_verify_apply` / `u_campus_binding` / `u_auth_token` / `u_favorite` / `u_address` / `u_cart_item` / `mk_user_coupon` / `n_notify_message` → CASCADE
   - `d_rider.user_id` → SET NULL
4. 删除成功后刷新列表与统计卡片。

## 3. 功能需求

### 后端
- FR-B01：新增 `PATCH /api/v1/platform/users/{userId}/verify`，body `{verifyStatus, expectedVerifyStatus, reason}`；仅 `verifyStatus ∈ {2,3}`，`expectedVerifyStatus ∈ {0,1,2,3}`；驳回必须带原因。
  - 通过允许当前状态 0/1/3；驳回仅允许当前状态 1。
- FR-B02：新增 `PATCH /api/v1/platform/users/{userId}/profile`，body 为可空字段集合，未传字段保持不变，传空串按「清空」处理。
- FR-B03：新增 `DELETE /api/v1/platform/users/{userId}`；存在订单时返回业务错误。
- FR-B04：`UserRow` 增加 `dormBuilding`、`verifyNote` 字段；列表查询列同步补齐。
- FR-B05：新增 Flyway `V5__user_verify_note.sql`，为 `u_user` 增加 `verify_note VARCHAR(255) NOT NULL DEFAULT ''`（用 information_schema 判重，兼容新库）。
- FR-B06：`AuthService.profile` 返回 `verifyNote`，供学生端展示驳回原因。
- FR-B07：以上接口复用 `ConsoleAccess.enforce`，仅 PLATFORM_ADMIN 可调用。

### 控制台（apps/console）
- FR-C01：用户列表行操作调整为：详情 / 编辑 / 审核（待审核、被驳回时）/ 封禁或解禁 / 删除；按钮不换行、不挤压表格。
- FR-C02：审核通过/驳回使用 `UiModal`，驳回时原因必填、提交中禁用按钮。
- FR-C03：编辑资料弹窗回填当前值，前端做最小校验（手机号格式、长度），错误直接 toast。
- FR-C04：删除确认弹窗展示后果说明；后端返回「存在订单」时在弹窗内展示错误，不关闭弹窗。
- FR-C05：详情弹窗补充宿舍楼、认证备注（verifyNote），并在底部提供「编辑资料 / 删除用户」。
- FR-C06：所有写操作成功后刷新列表，失败 toast 错误文案。

### 学生端（apps/h5，最小改动）
- FR-H01：个人页 `verifyStatus=3` 且 `verifyNote` 非空时，在认证标签下方展示「驳回原因：…」。

## 4. 非功能需求

- **权限**：仅平台管理员；商家账号调用返回 403（沿用 `ConsoleAccess`）。
- **并发**：审核与封禁均使用 expected 状态做 CAS，冲突返回「状态已变更，请刷新后重试」。
- **错误语义**：新增错误码 `USER_PHONE_EXISTS(60001)`、`USER_STUDENT_NO_EXISTS(60002)`、`USER_HAS_ORDERS(60003)`；其余沿用 `INVALID_PARAM` / `RESOURCE_NOT_FOUND`。
- **数据安全**：不返回 `password_hash`；编辑接口只更新白名单字段。
- **兼容**：`u_user.verify_note` 通过迁移新增，旧数据默认空串；新库由 V1 建表 + V5 补列。
- **测试**：
  - 后端单测覆盖：审核状态机与并发冲突、驳回原因必填/长度、资料字段校验与唯一冲突、删除订单守卫。
  - 控制台 `pnpm --filter @smartorder/console run typecheck` 通过。
  - 浏览器验证：待审核列表 → 通过 → 驳回 → 编辑手机号/学院/校区 → 删除有订单用户被拒 → 删除无订单用户成功。

## 5. 假设与约束

- 「新用户」指注册后 `verify_status=1` 的待审核用户；`verify_status=0` 的存量用户也可被直接「通过」。
- 驳回原因只保留最新一条（单列 `verify_note`），不做历史记录。
- 删除采用**物理删除 + 订单守卫**；有订单的用户通过「封禁」停用，避免订单/退款对账出现孤儿数据。
- 学生端不做资料自助编辑；平台代改后，学生下次登录/刷新 profile 即可看到新资料。
- 手机号/学号唯一冲突同时做前置查询与 `DuplicateKeyException` 兜底，避免并发下 500。

## 6. 验收标准（Acceptance Criteria）

| # | 类型 | 描述 |
|---|---|---|
| AC-01 | rule | 用户列表 `verifyStatus=1` 的行出现「通过 / 驳回」；点击通过后该行变「已认证」，统计卡「认证审核中」减 1 |
| AC-02 | rule | 驳回必须填原因；提交后该行变「认证驳回」，详情弹窗显示驳回原因 |
| AC-03 | rule | 审核使用 expected 状态；连续两次提交同一审核，第二次提示「状态已变更，请刷新后重试」 |
| AC-04 | rule | 编辑弹窗可修改手机号/学院/校区/宿舍楼/学号/昵称/姓名；保存后列表与详情立即反映新值 |
| AC-05 | rule | 将手机号改为其他用户已占用的号码时，提示「手机号已被其他用户使用」，数据不落库 |
| AC-06 | rule | 删除有订单记录的用户被拒绝，提示「该用户存在订单记录，为保证对账请改用封禁」 |
| AC-07 | rule | 删除无订单用户成功，列表移除该用户，统计卡总数减 1 |
| AC-08 | rule | 非平台管理员（商家账号 / 学生 token）调用三个新接口均返回 403/401 |
| AC-09 | rule | 学生端个人页认证被拒时展示后端返回的驳回原因 |
| AC-10 | rule | 后端 `mvn test` 相关用例通过；控制台 typecheck 无错误 |
| AC-11 | rubric | 交互一致性：新按钮沿用现有 `so-btn--sm` 尺寸与颜色语义（通过=ok、驳回/删除=danger） |
| AC-12 | rubric | 风险提示清晰：删除弹窗明确「不可恢复」及被清除的数据范围 |
