# 01 架构与技术选型

## 结论

| 层 | 选型 | 理由 |
|---|---|---|
| 用户端 | Vue 3 + Vite + Vant 4，移动端网页 | 学生不会为点饭装 App，扫码即开是硬需求 |
| 商家端 / 平台端 | Vue 3 + Vite + Element Plus，桌面网页 | 档口用电脑或平板接单，键盘操作效率高于手机 |
| 后端 | Node.js + NestJS + Prisma | 前后端同语言，类型可共享，单体足够 |
| 数据库 | MySQL 8.0 | 订单是强事务数据，关系型不可替代 |
| 缓存与队列 | Redis 7 | 菜单缓存、库存预扣、延迟队列、限流 |
| 实时通道 | SSE 为主，WebSocket 备用 | 单向推送够用，SSE 自动重连且更容易过代理 |
| 部署 | Docker Compose + Nginx | 一台 2 核 4G 服务器可承载整个校园体量 |

后端语言由你规划、暂不实现，所以这张表是建议而非既成事实。如果团队更熟 Java，把 NestJS 换成 Spring Boot、Prisma 换成 MyBatis-Plus，数据库设计与接口契约完全不变，本系列文档其余部分照用。

## 为什么纯 Web 在校园反而是优势

我先前判断小程序是唯一答案，那个结论下得太早。Web 形态在校园里有一个小程序拿不到的能力：**统一身份认证**。

绝大多数高校已部署 CAS 或基于 OAuth2 的一卡通门户。学生用学号密码登录一次即可拿到身份，不需要注册、不需要上传学生证、不需要人工审核学籍。`u_campus_binding` 表就是为这条链路准备的。小程序里这条链路走不通，只能靠手机号加人工审核，运营成本高得多。

代价集中在两处，都需要提前接受。

触达能力变弱。小程序有订阅消息，网页没有常驻推送。方案是三层兜底：页面在前时用 SSE 实时推，页面不在时写站内信并记在 `n_notify_message`，出餐这个真正紧急的节点额外发一条短信。`retry_count` 与 `last_error` 两列就是为短信重发准备的。

支付通道受限。普通浏览器的 H5 支付需要微信支付商户号加备案域名，学生团队通常申请不到商户号。`p_payment.channel` 设计成字符串枚举而不是布尔，配合 `sys_config.PAYMENT_ENABLED_CHANNELS`，就是为了让渠道可以先只开 `MOCK`、后续逐个放开，业务代码不动。详见第 4 节。

## 单体，不拆微服务

判断依据是量级而非时髦。校园餐饮的订单集中在下课后四十分钟，全天峰值按一万单算，平均不到 0.2 单每秒，峰值放大五十倍也只有每秒十几单写入。这个量级单个 Node 进程远远吃不满，拆服务只会把一次函数调用变成一次网络调用，把一个问题排查变成六个日志文件。

真正的瓶颈在别处：午高峰的菜单读请求可能有几百 QPS，靠 Redis 缓存解决；库存扣减是行锁竞争，靠 Redis 预扣解决。这两件事在单体里同样能做。

模块边界用目录划分，不用进程划分。若将来某天确实要拆，按 `docs/03` 的模块目录整体搬走即可。

## 部署拓扑

```
                 校园网 / 公网
                      │
                 Nginx(:443, TLS)
                  │         │
        /api →  app(:3000)  / → 静态资源(两个前端构建产物)
                  │
        ┌─────────┼─────────┐
     MySQL(:3306) Redis(:6379)  定时任务(进程内)
```

compose 起四个容器：`nginx`、`app`、`mysql`、`redis`。单机部署，MySQL 与 Redis 不暴露公网端口，只在 compose 内网可达。

数据量估算。一万单每天，每单约 2.5 个明细行，一年约 3650 万行订单。`o_order` 主表按每行 400 字节算一年约 15 GB，含索引约 25 GB。三年数据量在机械盘可承受范围，但查询会开始变慢。所以设计上一开始就把 `biz_date` 放进索引最左列，后续按它做范围归档或直接加分区，不需要改表结构。

## 服务器与域名

配置建议 2 核 4G 起步，40G SSD。学生团队可申请的免费或低价途径：学校信息中心的主机托管（最省钱，且通常免备案流程）、云厂商学生机（2 核 2G 约百元一年，内存偏小需给 MySQL 调低缓冲池）。

**ICP 备案是最长的一条外部依赖，通常 7 到 20 个工作日。** 如果要用学校机房的主机，备案主体是学校，需要走信息中心审批，周期更不可控。这件事必须在第一周启动，否则代码写完也上不了线。

## 环境划分

三套环境，配置全部走环境变量，不允许代码里出现环境判断常量。

`dev` 本机 Docker 起 MySQL 与 Redis，前端 Vite 代理到后端，关闭限流与真实短信。

`staging` 与生产同构，接学校 CAS 测试地址，用于验收登录链路。

`prod` 只有这一套有真实订单。上线前必须确认 `PAYMENT_ENABLED_CHANNELS` 与 `MIN_VERIFY_STATUS_TO_ORDER` 两个配置的取值，后者设成 0 会导致游客可下单，内测放量时方便，忘了改回来就是事故。
