# 01 架构与技术选型

## 结论

| 层 | 选型 | 理由 |
|---|---|---|
| 学生端 | Vue 3 + Vite，移动网页（h5）用 Vant 4，桌面网页（web）自建设计令牌 | 学生不会为点饭装 App，扫码即开是硬需求；桌面形态覆盖食堂高峰在电脑上下单的场景 |
| 商家端 / 平台端 | Vue 3 + Vite，桌面网页，自建组件与样式 | 档口用电脑或平板接单，键盘操作效率高于手机；控制台页面形态固定，自建组件比引 Element Plus 更可控 |
| 后端 | Spring Boot 3.2.5 + Java 17 + MyBatis-Plus，Flyway 迁移，JJWT 鉴权 | 单体足够，事务与行锁语义直接落在 MySQL 上；不引 Spring Security，一个 OncePerRequestFilter 完成鉴权 |
| 数据库 | MySQL 8.0 | 订单是强事务数据，关系型不可替代 |
| 缓存与队列 | 暂未引入，Redis 7 是二期选项 | 当前量级直查 MySQL 即可；超时关单靠定时扫表，菜单缓存与库存预扣等压测证明瓶颈后再上 |
| 实时通道 | SSE | 单向推送够用，自动重连且更容易过代理；服务端 3 秒兜底扫描加客户端降级轮询 |
| 部署 | 生产规划 Docker Compose + Nginx；开发用 start.bat 一键引导 | 一台 2 核 4G 服务器可承载整个校园体量 |

后端已按上表落地，代码在 `server/`，接口契约与实现口径见 `docs/03`。数据库设计自始至终没有变过，`db/schema.sql` 是唯一真源。

## 为什么纯 Web 在校园反而是优势

我先前判断小程序是唯一答案，那个结论下得太早。Web 形态在校园里有一个小程序拿不到的能力：**统一身份认证**。

绝大多数高校已部署 CAS 或基于 OAuth2 的一卡通门户。学生用学号密码登录一次即可拿到身份，不需要注册、不需要上传学生证、不需要人工审核学籍。`u_campus_binding` 表就是为这条链路准备的。小程序里这条链路走不通，只能靠手机号加人工审核，运营成本高得多。

代价集中在两处，都需要提前接受。

触达能力变弱。小程序有订阅消息，网页没有常驻推送。方案是三层兜底：页面在前时用 SSE 实时推，页面不在时写站内信并记在 `n_notify_message`，出餐这个真正紧急的节点额外发一条短信。`retry_count` 与 `last_error` 两列就是为短信重发准备的。

支付通道受限。普通浏览器的 H5 支付需要微信支付商户号加备案域名，学生团队通常申请不到商户号。`p_payment.channel` 设计成字符串枚举而不是布尔，配合 `sys_config.PAYMENT_ENABLED_CHANNELS`，就是为了让渠道可以先只开 `MOCK`、后续逐个放开，业务代码不动。当前实现只开了 `MOCK`，渠道回调与真实退款见 `docs/04` 第 3 节。

## 单体，不拆微服务

判断依据是量级而非时髦。校园餐饮的订单集中在下课后四十分钟，全天峰值按一万单算，平均不到 0.2 单每秒，峰值放大五十倍也只有每秒十几单写入。这个量级单个 JVM 进程远远吃不满，拆服务只会把一次函数调用变成一次网络调用，把一个问题排查变成六个日志文件。

真正的瓶颈在别处：午高峰的菜单读请求可能有几百 QPS，库存扣减是行锁竞争。当前实现直查 MySQL，靠 `idx_o_merchant_board` 等覆盖索引与行锁守卫撑住；菜单缓存与 Redis 预扣是压测证明瓶颈后的二期优化，见 `docs/04` 第 5、7 节。这两件事在单体里同样能做。

模块边界用目录划分，不用进程划分。若将来某天确实要拆，按 `docs/03` 的模块目录整体搬走即可。

## 部署拓扑

```
                 校园网 / 公网
                      │
                 Nginx(:443, TLS)
                  │         │
        /api →  app(:8080)  / → 静态资源(三个前端构建产物)
                  │
        ┌─────────┴─────────┐
     MySQL(:3306)      定时任务(进程内 @Scheduled)
```

生产按 compose 起 `nginx`、`app`、`mysql` 三个容器，Redis 在启用缓存与预扣后再加。单机部署，MySQL 不暴露公网端口，只在 compose 内网可达。当前开发环境不用 Docker：`start.bat` 把 JDK 17、Maven、Node、便携 MySQL 8.0.40 下载进 `.tools/`，MySQL 监听 3307，后端 8080，三个 Vite dev server 分别监听 5173/5174/5175 并把 `/api` 代理到 8080。

数据量估算。一万单每天，每单约 2.5 个明细行，一年约 3650 万行订单。`o_order` 主表按每行 400 字节算一年约 15 GB，含索引约 25 GB。三年数据量在机械盘可承受范围，但查询会开始变慢。所以设计上一开始就把 `biz_date` 放进索引最左列，后续按它做范围归档或直接加分区，不需要改表结构。

## 服务器与域名

配置建议 2 核 4G 起步，40G SSD。学生团队可申请的免费或低价途径：学校信息中心的主机托管（最省钱，且通常免备案流程）、云厂商学生机（2 核 2G 约百元一年，内存偏小需给 MySQL 调低缓冲池）。

**ICP 备案是最长的一条外部依赖，通常 7 到 20 个工作日。** 如果要用学校机房的主机，备案主体是学校，需要走信息中心审批，周期更不可控。这件事必须在第一周启动，否则代码写完也上不了线。

## 环境划分

三套环境，配置全部走环境变量，不允许代码里出现环境判断常量。

`dev` 用 `start.bat` 一键引导：便携 MySQL 起在 3307，Flyway 建库灌种子，后端与三个前端一起拉起。短信是开发桩（验证码固定 `000000`，不接真实网关），控制台演示账号统一密码 `demo123456`，限流未实现。这些开发便利都标了 `TODO(上线前)`。

`staging` 与生产同构，接学校 CAS 测试地址，用于验收登录链路。

`prod` 只有这一套有真实订单。上线前必须确认 `PAYMENT_ENABLED_CHANNELS` 与 `MIN_VERIFY_STATUS_TO_ORDER` 两个配置的取值，后者设成 0 会导致游客可下单，内测放量时方便，忘了改回来就是事故。
