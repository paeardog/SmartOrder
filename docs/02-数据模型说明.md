# 02 数据模型说明

34 张表、450 列、71 个索引（唯一 25）、23 个外键。完整 DDL 见 `db/schema.sql`，最近一次校验输出见 `db/schema-report.txt`。本文只讲为什么这么设计。

## 六条建表约定

**金额一律用「分」存整数。** 所有金额列类型是 `INT UNSIGNED` 或 `BIGINT UNSIGNED`，没有任何 `FLOAT`、`DOUBLE`、`DECIMAL`。浮点做加法会出现 `0.1 + 0.2 !== 0.3`，对账时查不清来源；`DECIMAL` 精确但在驱动层会变成字符串或高精度对象，前端处理麻烦。用最小货币单位存整数是唯一正确做法。评分同理：`rating_score` 存 `478` 表示 `4.78`，除以 100 在前端做。

**订单明细是全量快照，永不回查菜品表。** `o_order_item` 里存了 `dish_name`、`dish_image`、`category_name`、`option_text`、`unit_price`。档口改名、换图、调价、下架，历史订单必须原样还原，否则用户翻昨天的订单会看到价格变了。`dish_id` 只用于销量回溯，不用于展示。

**面向用户的单号和自增主键分离。** `order_no`、`payment_no`、`refund_no` 是对外标识，`id` 只在内部关联。自增 ID 暴露在外会泄露业务量，也让越权测试变得 trivial（把 `order_id` 从 1001 改成 1002 就能看别人的订单）。

**状态变更必须留痕。** `o_order_status_log` 记录每一次流转的操作者类型、操作者 ID、操作者姓名快照与备注。客诉时这是唯一能对上质的依据。姓名存快照而不是关联查询，是为了三年后这个员工离职了日志依然可读。

**软删除的唯一约束要挂 `deleted_flag` 而不是 `deleted_at`。** 这条最容易写错，见下文。

**表名按域加前缀。** `sys_` 系统、`u_` 用户、`m_` 商家菜品、`o_` 订单、`p_` 支付、`mk_` 营销、`d_` 配送、`n_` 通知、`st_` 统计。写查询时不需要想表在哪。

## 菜品为什么要三层

`m_dish` 是 SPU，`m_dish_option_group` 是规格组，`m_dish_option` 是具体选项。因为食堂的真实需求是「辣度单选必选、份量单选、加料多选各加价」三种语义混在一起。

`group_type` 区分 `SPEC`（互斥单选）和 `TOPPING`（多选加价），配合 `required`、`min_select`、`max_select` 描述约束，前端可以纯数据驱动渲染选择器，后端可以通用校验，加一个新菜品不需要改代码。

`m_dish_option.stock` 单独给加料设库存。鸡蛋卖完了，「加卤蛋」要能置灰，而不是让用户下单之后商家打电话退款。`-1` 表示不限。

## 库存为什么独立成表

`m_dish_stock` 按 `(dish_id, biz_date)` 存 `stock_total`、`stock_locked`、`stock_sold`。可用量是 `total - locked - sold`。

不放 `m_dish.stock` 一列，原因有两个。食堂的备货是按天重新来的，今天剩多少不代表明天有多少；而「下单未出餐」和「已完成」对库存的影响不同，取消订单要把 `locked` 还回去，出餐完成才真正扣减。三个数字分开存，退款和取消才能准确回补。

## 软删除与唯一索引

第一版把唯一索引写成 `UNIQUE (merchant_id, name, deleted_at)`，认为这样能保证「同名菜品只能有一个有效记录，删除的不算」。这是错的。

MySQL 的唯一索引不约束 `NULL`。有效行的 `deleted_at` 恒为 `NULL`，于是 `(1, '鱼香肉丝盖饭', NULL)` 可以无限插入，活跃数据的重复校验彻底失效——恰恰是需要它生效的那一半不起作用。

正确做法是加一列 `deleted_flag`：有效时为 `0`，删除时回写为自身 `id`。

```
UNIQUE (merchant_id, name, deleted_flag)
```

有效行 `deleted_flag` 全为 `0`，非 `NULL`，唯一约束正常生效。删除行各自等于自身 id，彼此不撞，同一名字删了还能再建。

## 可空列与唯一索引

校验器对三处给出了提示，三处都是有意为之。

`u_user.phone` 可空且有唯一索引。走统一身份认证的学生可以不提供手机号，MySQL 允许多行 `NULL` 共存于唯一索引，所以纯 SSO 用户不会互相撞键。若把 `phone` 改成 `NOT NULL DEFAULT ''`，空串参与唯一约束，第二个不填手机号的用户就会插入失败。

`d_rider.user_id` 同理，外键动作是 `ON DELETE SET NULL`，骑手注销学生账号时不应连带删除配送历史。

`o_order.pickup_code` 是这条规则的真实教训。它最初写成 `CHAR(6) NOT NULL DEFAULT ''`，静态校验一切正常，种子数据也插得进去——因为五张样例订单刚好没有踩到。在真实 MySQL 上插同档口同日第二张未出餐订单时立刻报错：

```
ERROR 1062 (23000): Duplicate entry '1-2026-11-16-' for key 'o_order.uk_o_pickup_code'
```

未出餐的订单取餐码都是空串，于是「同档口同日所有待出餐订单」在唯一索引里互相冲突。这个系统连第二单都下不出去，而它与上线第一次午高峰之间没有任何缓冲。改成 `pickup_code CHAR(6) NULL` 后，未分配的行不参与唯一约束，已分配的码仍然唯一。

校验器现在多了一条规则拦住同类问题：唯一索引里的字符列如果是 `NOT NULL DEFAULT ''`，直接判定为错误。

## 数量列同样要 UNSIGNED

`m_dish_stock` 的 `stock_total`、`stock_locked`、`stock_sold` 原本是有符号 `INT`。探针证明有符号列允许 `stock_locked` 被写成 `-500`——一次重复触发的库存释放就会污染数据，而且没有任何报错，之后所有可用量计算都偏高，直到超卖才被发现。改成 `INT UNSIGNED` 后同一条语句被数据库拒绝：

```
ERROR 1690 (22003): BIGINT UNSIGNED value is out of range in '(...stock_locked - 500)'
```

`u_sms_code.send_count`、`u_sms_code.fail_count`、`n_notify_message.retry_count`、`st_dish_daily.stock_total` 一并改为 `UNSIGNED`。数据库能兜住的错误不该留给代码 review。

由此确定一条写代码的规矩：算可用量一律用加法形式 `WHERE stock_total >= stock_locked + stock_sold + :n`，不要写 `WHERE stock_total - stock_locked - stock_sold >= :n`。后者在不变量被破坏时会因为无符号下溢抛 1690，把一条本该返回零行的查询变成异常。

`m_dish_option.stock` 原本用 `-1` 表示「不限量」，因此整列不得不保持有符号。哨兵值和真实数量混在同一列里会出错：扣减 SQL 把 `-1` 减成 `-2`，之后的 `stock >= n` 判断就把它当成售罄，一个本来不限量的加料在第一次被选中后再也买不了。现在改为 `SMALLINT UNSIGNED NULL`，`NULL` 表示不限量，扣减语句带 `AND stock IS NOT NULL` 直接跳过不限量的行，测试 `19-option-stock-nullable.sql` 验证了不限量行不受守卫影响。校验器也对数量列增加了「默认值不得为负」的检查。

## 为什么订单表不建外键

`o_order` 的 `user_id`、`merchant_id` 都没有外键约束，`st_*` 汇总表也没有。这是刻意的，列注释里也写明了原因。

订单表是写入最频繁、留存最久的表。外键约束在每次插入时都要去父表加共享锁校验，午高峰会成为可测量的开销。更重要的是运营需要能力：封禁或注销一个违规档口、清理一个毕业生账号，都不应该被「还有历史订单引用它」挡住。历史订单必须能永久查询。

引用完整性由应用层在下单事务里校验（菜品与档口是否存在且可用），加上冗余快照列兜底。`o_refund.user_id`、`st_dish_daily.merchant_id` 这类明显是复制过来的字段，注释里都标了「冗余」，避免后来者误以为它们有约束。

## 索引设计要点

`o_order` 有四个业务索引，各自对应一个高频查询：

| 索引 | 服务的查询 |
|---|---|
| `idx_o_merchant_board (merchant_id, status, biz_date, id)` | 商家接单台每秒轮询的「本店今日待处理」，覆盖过滤、排序与分页 |
| `idx_o_user_list (user_id, biz_date, id)` | 学生的订单列表 |
| `idx_o_timeout (status, expire_at)` | 支付超时兜底扫描，详见 `docs/04` |
| `idx_o_pending_board (status, pickup_deadline_at)` | 出餐后超时未取的自动完成扫描 |

`uk_o_pickup_code (merchant_id, biz_date, pickup_code)` 保证同一档口同一天取餐码唯一，`pickup_code` 在出餐前为 `NULL`（见上一节）。码位在出餐时分配，不回收——取消订单占用的当天编号不重新发放。四位数字有一万种组合，单日单档口不可能用完，用一点码空间浪费换掉「两个用户拿着同一个码取同一份饭」的风险，值得。

`EXPLAIN` 在真实 MySQL 8.0.40 上逐条验证过这四个索引确实被选中，不是纸面推演：

| 查询 | type | key | Extra |
|---|---|---|---|
| 超时扫描 `status = 'PENDING_PAYMENT' AND expire_at < NOW(3)` | `range` | `idx_o_timeout` | Using index condition |
| 接单台 `merchant_id = 1 AND status = 'PAID' AND biz_date = CURDATE() ORDER BY id DESC` | `ref` | `idx_o_merchant_board` | Backward index scan |
| 订单列表 `user_id = 1 AND biz_date = CURDATE() ORDER BY id DESC` | `ref` | `idx_o_user_list` | Backward index scan |
| 取餐码核销 `merchant_id = 1 AND biz_date = CURDATE() AND pickup_code = '1024'` | `const` | `uk_o_pickup_code` | Using index |

`ORDER BY id DESC` 走 `Backward index scan` 而不是 filesort，说明索引尾列 `id` 的作用达到预期。核销查询命中 `const` 且 `Using index`，不需要回表。

## 种子数据

`db/seed.sql` 是三个真实档口：川香盖浇饭（含规格与加料）、兰州牛肉面（含限量售罄的牛杂面）、悸动奶茶（糖度冰量加料），外和一个待审核状态的档口用于验证审核流。五张订单覆盖 `READY`、`PENDING_PAYMENT`、`ACCEPTED`、`COMPLETED`、`CANCELLED` 五种状态，前端可以据此调通接单台的全部状态分栏。控制台账号也在种子里：`admin`（平台）、`chuanxiang` / `lanzhou` / `jido`（三家档口老板）、`chuanxiang02`（川香店员），密码哈希是 `$argon2id$dev-placeholder` 占位符，开发期统一密码由 `application-dev.yml` 的 `dev-account-password` 决定（`demo123456`，`TODO(上线前)`）。学生的口令散列、券模板、持券与收货地址示例不在 seed 里，在 `V2` / `V3` 迁移里，原因见下文。

种子数据里所有金额都通过了恒等式校验，包括 `line_amount = unit_price × quantity + pack_fee - discount_amount`、订单金额等于明细合计、支付金额等于订单实付。这些是 `scripts/check-schema.mjs` 的实际检查项，不是人工核对的承诺。

## 已执行的验证与未覆盖的部分

`db/schema.sql` 与 `db/seed.sql` 在本地 MySQL 8.0.40 上真实执行过。当前开发库（含 Flyway 迁移）回查 `information_schema` 的结果：34 张业务表全部建成（另有 `flyway_schema_history`），`ENGINE=InnoDB`、`COLLATE=utf8mb4_unicode_ci` 各 34/34，23 个外键全部建立成功。索引共 106 个（唯一 59，含 34 个主键），`STATISTICS` 按列展开共 185 条记录；本文开头静态报告的 71 个索引（唯一 25）只数 DDL 显式声明的二级索引，不含主键，库侧另有一个外键自动索引，两种口径数字不同但结构一致。非金额类的 `DECIMAL` 只有 `u_pickup_point` 的经纬度两列。种子写入 23 张表共 185 行，金额恒等式由 `scripts/check-schema.mjs` 在每次 `pnpm run check` 时对种子重算，五张样例订单的明细、订单头、支付三层金额全部自洽。

19 个行为测试已收进 `db/tests/`，`pnpm run test:db` 重建库、灌种子、逐个断言。覆盖：取餐码唯一约束的正反两面、幂等键撞库、外键拦截、状态机 CAS 的三种影响行数、库存条件扣减与守卫释放、无符号列的越界拒绝、加料库存的 `NULL` 不限量语义、JSON 取值、`DATETIME(3)` 毫秒精度、服务端时区 `+08:00`、utf8mb4 存 emoji、软删后重建同名菜品、购物车规格哈希去重，以及上面那四条 `EXPLAIN`。

没有覆盖的：并发。单实例连接下这些语句都是顺序执行，真正决定正确性的是两个事务同时抢同一行库存时的行为，需要压测或多连接事务脚本才能证明。事务隔离级别实测为 `REPEATABLE-READ`、`innodb_autoinc_lock_mode = 2`，这两项会影响后端实现，已记入 `docs/04`。

## 后端接入时踩到的两个环境坑

第一个是 JDBC 时区参数。连接串最初写的是 `connectionTimeZone=Asia/Shanghai&forceConnectionTimeZoneToSession=true`，驱动会把它翻译成 `SET time_zone='Asia/Shanghai'`。这条语句要求 `mysql.time_zone_name` 里有命名时区，而命名时区表不是装好就有的，得用 `mysql_tzinfo_to_sql` 导进去。本机那份 8.0.40 是解压自用的，从没导过，实测 `SELECT COUNT(*) FROM mysql.time_zone_name` 返回 0，于是启动即失败：

```
java.sql.SQLException: Unknown or incorrect time zone: 'Asia/Shanghai'
ERROR 1298 (HY000): Unknown or incorrect time zone: 'Asia/Shanghai'
```

同一连接里 `SET time_zone='+08:00'` 立即成功，说明问题只在命名时区缺数据。现在两份配置都改成数字偏移，写成 `%2B08:00`——`+` 在 URL 里必须转义，否则解出来是空格，又是一次静默的错值。代价是数字偏移不跟着夏令时走，但学校只在一个时区运营，这个代价为零；真要在多时区部署，正确做法是补时区表而不是改代码。

第二个是 Flyway 与既有库的关系。`db/schema.sql` 是设计产物，已经手工建过库；Flyway 面对一张有 31 个表却没有 `flyway_schema_history` 的库会直接拒绝：

```
Found non-empty schema(s) `smartorder` but no schema history table.
Use baseline() or set baselineOnMigrate to true to initialize the schema history table.
```

配置取 `baseline-on-migrate: true` 加 `baseline-version: 0`，含义是承认库里已有的结构、把历史表基线打在 0，然后照常应用 `V1`。`V1__baseline.sql` 由 `scripts/gen-flyway.mjs` 从 `schema.sql` 生成，只保留 `CREATE TABLE` 并改写成 `IF NOT EXISTS`，所以对已建成的库是空操作，对全新环境则一步建齐。`pnpm run check:flyway` 会重新生成并与仓库里的文件逐字节比对，防止设计脚本和迁移脚本各走各路。种子数据原则上不进迁移，生产库要的是空表，示例档口只属于开发环境。`V2` 与 `V3` 是有意的例外：`V2` 写入学生的 PBKDF2 口令散列、券模板、持券、收货地址的示例行，因为它们依附的三张表正是 `V2` 建的；`V3` 写入学生端演示账号 `admin` / `admin`，带 `WHERE NOT EXISTS` 守卫，上线前删除或改密。这条例外决定了 `reset` 不能只灌 `schema.sql` 与 `seed.sql`，见文末「`reset` 到底做了什么」。

`schema.sql` 后续补了表，`gen:flyway` 重新生成的 `V1` 内容就变了，校验和跟着变。Flyway 开着 `validate-on-migrate: true`，跑过迁移的库下次启动会拒绝：

```
Migration checksum mismatch for migration version 1
```

这不是数据坏了，是历史表里记的校验和与磁盘上的文件对不上。`flyway repair` 只重写 `flyway_schema_history` 那一行，不动业务表；`start.bat reset` 重建业务表并清掉历史表，让迁移从头再跑，开发机上更省事，但会丢掉本地数据。两种都行，别改配置去关校验——关掉的代价是真正的迁移文件被误改时也没人报警。

`V1` 之后的版本要能在两种库上都跑通：全新库里结构已由 `schema.sql` 与 `V1` 一次建齐，老库里还缺列缺索引。`ALTER TABLE ... ADD COLUMN`、`DROP INDEX` 这类语句在前一种库上是硬错误（`1060 Duplicate column`、`1091 Can't DROP`），而 Flyway 一个版本失败就卡住后面所有版本。所以 `V2` 的四处结构改动都先查 `information_schema.COLUMNS` / `STATISTICS` 决定执行还是跳过，用 `SET @sql = (SELECT IF(...))` 加 `PREPARE`/`EXECUTE` 完成，不引 `DELIMITER` 也不建存储过程——那两样在迁移脚本里只会带来更多坑。新增结构改动照这个写法来，改完除了 `check:flyway` 要绿，还得在全新库和老库升级两条路上各跑一遍才算验过。

## `reset` 到底做了什么

`start.bat reset` 是四步，顺序不能换：删 `flyway_schema_history`、执行 `db/schema.sql`、执行 `db/seed.sql`、按文件名顺序重放 `server/src/main/resources/db/migration/V*.sql`。

删历史表是因为它不在 `schema.sql` 的 DROP 清单里，业务表被重建了而它还留着 `V2 success=1`。留着的那次实测结果是：库重建成功、后端启动时 Flyway 认为 `V2` 跑过不再执行，于是 `u_user.password_hash` 停在 `seed.sql` 写入的空串，`mk_coupon_template`、`mk_user_coupon`、`u_address` 三张表是空的，任何学号都登录不上，报 `20008`。表齐了但数据不齐，比直接报错更难查。

重放迁移是为了让 `reset` 单独跑完就能用，不必再重启一次后端等 Flyway。`V1` 全是 `CREATE TABLE IF NOT EXISTS`，`V2` 的结构改动都带 `information_schema` 守卫、数据改动是 `INSERT IGNORE` 与按 `student_no` 定位的 `UPDATE`，所以同一条迁移被执行两次是安全的——`reset` 用客户端跑一遍，后端启动时 Flyway 再记一遍历史，结果一致。代价是 `V2` 里那些 `SELECT 1` 空分支会往 `reset` 的输出里打几行 `1`，看着乱但无害；改 `V2` 的文本会让校验和变化，逼所有已有库 repair 或 reset，不值得。

每一步都检查客户端退出码，任何一步失败就停下并说明库里现在缺什么。这一步是补上的：早先 `reset` 不检查退出码，`mysql` 读批处理文件遇到错误会中断，脚本却继续往下灌种子数据，最后留下一个只有十几张表的库，而屏幕上什么都没说。

`schema.sql` 的 DROP 清单必须覆盖它自己建的每一张表，这是 `reset` 能重跑的前提。这个不变量先前靠人工维持，`V2` 补的三张表加进了 `CREATE` 却没加进 `DROP`，于是第二次 `reset` 走到那三条 `CREATE TABLE` 撞 `1050 Table already exists` 中断，库里只剩前面建好的十三张表。现在 `scripts/check-schema.mjs` 直接比对两侧的表名，缺 DROP 就报错误项，`pnpm run check` 与 `start.bat check` 都会挡下来，不再依赖上一次手动跑成功。

## 开发库的账号与口令

`start.bat` 管的这份便携 MySQL 用 `root` / `123456`，`127.0.0.1:3307`，`DB_PASS` 可以改。口令不写在命令行上：`build_client_args` 把它放进 `MYSQL_PWD` 环境变量，`mysql` 与 `mysqladmin` 都认，否则每次调用都会往输出里打一行 `Using a password on the command line interface can be insecure`，一次 `reset` 能刷出十几行。后端侧 `application-dev.yml` 写 `${DB_PASSWORD:123456}`，`start.bat` 另外导出 `SPRING_DATASOURCE_PASSWORD`，两条路都指向同一个值。

授权落在 `.tools\init-grants.sql`，由 `:write_ini` 每次运行时按当前 `DB_PASS` 重新生成，mysqld 通过 `init-file` 在启动时执行它。这里有个容易踩的点：`CREATE USER IF NOT EXISTS ... IDENTIFIED BY` 对已存在的账号是空操作，不会改口令，所以文件里紧跟一条 `ALTER USER`。少了它，改了 `DB_PASS` 再重启 mysqld，库里还是旧口令，客户端却拿新口令去连，表现为一片 `Access denied`。同一个 ini 的 `[client]` 段也写了 `password`，手工敲 `mysql --defaults-file=.tools\my-3307.ini` 就不用再带口令。

改口令要动四处：`init-grants.sql` 的生成逻辑、`application-dev.yml`、`scripts/run-db-tests.mjs` 的 `DB_PASS` 默认值、README。已经在跑的实例不会自己跟上，`init-file` 只在 mysqld 启动时执行一次，所以对现有库要补一条 `ALTER USER 'root'@'127.0.0.1' IDENTIFIED BY '<新口令>'`（`'root'@'localhost'` 同理），并且后端要重启——连接池里那些已认证的连接还能用，等 Hikari 按 `max-lifetime` 回收后新建连接才会用新口令，故障是延迟出现的，比立刻报错更难认。
