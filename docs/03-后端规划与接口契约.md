# 03 后端规划与接口契约

后端尚未实现。本文是施工图纸，`docs/04` 补充其中的难点实现细节。

## 模块划分

NestJS 单体，按业务域分模块，模块之间通过 service 注入调用，禁止跨模块直接查表。

```
src/
  main.ts                    全局管道、拦截器、异常过滤器
  common/
    decorators/              @CurrentUser @Idempotent @RateLimit
    filters/                 HttpExceptionFilter，统一错误响应
    interceptors/            响应包装、耗时埋点
    pipes/                   数值与枚举校验
    idempotency/             幂等中间件
  modules/
    auth/                    CAS 对接、短信验证码、JWT 签发与轮换
      strategies/cas.strategy.ts
      services/cas.service.ts     ticket 校验与属性映射
      services/token.service.ts   refresh token 落 u_auth_token
    user/                    学生档案、学籍认证、收藏、地址
    merchant/                档口 CRUD、营业时段、临时歇业、审核
    menu/                    分类、菜品、规格组、规格项、每日库存
    cart/                    服务端购物车
    order/                   下单、状态机、取消、核销、列表与详情
      state-machine.ts       唯一的合法流转表
      services/create.service.ts   下单主流程，事务边界在这里
      services/timeout.service.ts  延迟队列消费与兜底扫描
    payment/                 支付编排与渠道适配
      providers/provider.interface.ts
      providers/mock.provider.ts
      providers/wxpay-h5.provider.ts   拿到商户号后再写
      callback.controller.ts            渠道回调入口
    refund/                  退款申请、审核、渠道退款
    fulfillment/             配送相关，一期只提供接口骨架
    notify/                  站内信、SSE 推流、短信
    stats/                   日汇总回写、报表查询
    config/                  sys_config 读取，带 Redis 缓存
  jobs/
    scheduler.ts             定时任务注册入口
    tasks/                   各具体任务
  prisma/schema.prisma
```

Prisma schema 从 `db/schema.sql` 生成（`prisma db pull`），之后以 migration 为唯一变更来源，不再手写 DDL。两者一旦分叉，排错成本极高。

## 鉴权

两套独立的守卫，互不通用。

学生端走 JWT。`access token` 有效期 15 分钟，只放 `userId`、`verifyStatus`、`campusArea`。`refresh token` 有效期 30 天，随机 64 字节，库里只存 SHA-256 摘要（`u_auth_token.token_hash`），每次刷新旧值作废、新值入库。这样登出、改密、封禁都能立即生效，纯无状态 JWT 做不到。

登录链路优先统一身份认证：前端跳 CAS 登录页，回跳带 `ticket`，后端拿 `ticket` 加自己的 `service` 地址回调 CAS 的 `serviceValidate`，解析返回的学号与属性，查 `u_campus_binding` 建或更新用户，签发自己的双 token。这一步必须在测试环境对接学校真实地址验证，属性字段名各校不一（有人叫 `userId`，有人叫 `personNumber`），映射表写在 `config` 里。

兜底是手机号加短信验证码。商家与平台账号是用户名密码，argon2id 哈希，独立于学生体系。

## 接口契约

响应统一包装，`code` 为 0 表示成功，非 0 是业务错误码。HTTP 状态码只表达传输层结果，业务失败一律 200 加非零 `code`，避免前端在拦截器里做双重判断。

```
{ "code": 0, "message": "ok", "data": { }, "traceId": "..." }
```

分页统一 `page` 从 1 起、`pageSize` 上限 100，返回 `{ list, total, page, pageSize }`。列表一律倒序按 `id`，不按 `created_at`，因为同秒并发写入时排序不稳定会导致翻页重复或漏项。

标量类型有两条硬约定。所有 `BIGINT` 主外键序列化成字符串，Java 侧由 `JacksonConfig` 给 `Long` 注册 `ToStringSerializer` 全局生效，前端不参与 ID 运算、只做等值比较与回传；数字照常输出会有真实代价，`order_id` 超过 2^53 后 `JSON.parse` 会静默改变取值，这种错在页面上看不出来。所有时间统一带偏移的 ISO-8601，例如 `2026-11-16T12:13:31.727+08:00`。库里存的是 `DATETIME(3)` 墙上时间，JDBC 连接强制会话时区 `+08:00`，出口由序列化器按 `smartorder.zone-id` 补上偏移。裸的 `2026-11-16T12:13:31.727` 会被浏览器按访问者本地时区解析，运营人员和学生在同一套系统里会看到不同的时间；带偏移则不存在这个歧义，而 `Zulu` 或毫秒时间戳又让日志对不齐。反序列化两种都收，偏移形式先换算到 `zone-id` 再入库，本地形式按墙上时间直接采用，方便管理后台手填。

### 认证

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/auth/cas/redirect` | 返回 CAS 登录跳转地址 |
| POST | `/api/auth/cas/callback` | 校验 ticket，返回双 token |
| POST | `/api/auth/sms/send` | 发验证码，按手机号与 IP 双维度限流 |
| POST | `/api/auth/sms/verify` | 验证码登录 |
| POST | `/api/auth/refresh` | 刷新，旧 refresh 立即作废 |
| POST | `/api/auth/logout` | 撤销当前 refresh |

### 菜品与购物车

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/merchants` | 按校区与营业状态列档口，走缓存 |
| GET | `/api/merchants/:id/menu` | 分类、菜品、规格组、库存一次返回，避免前端串行请求 |
| GET | `/api/dishes/:id` | 单品详情，含规格可选性与剩余量 |
| GET | `/api/cart` | 服务端购物车，按档口分组 |
| POST | `/api/cart/items` | 加购，`optionHash` 冲突则累加数量 |
| PATCH | `/api/cart/items/:id` | 改数量或勾选态 |
| DELETE | `/api/cart` | 清空，可带 `merchantId` 只清一家 |

`GET /api/merchants/:id/menu` 是全天 QPS 最高的接口，返回体必须带 `serverTime` 与 `stockVersion`：前者让前端判断是否打烊不依赖本机时钟，后者用于缓存失效判断。

### 下单与订单

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/orders` | 下单，**必须**带 `X-Client-Order-No` 请求头 |
| GET | `/api/orders` | 我的订单，`status` 可选 |
| GET | `/api/orders/:orderNo` | 详情，按业务单号而非自增 id |
| POST | `/api/orders/:orderNo/cancel` | 用户取消，受 `USER_CANCEL_WINDOW_SECONDS` 限制 |
| POST | `/api/orders/:orderNo/preflight` | 结算页价格与库存预校验，返回最终应付金额 |

下单请求体只允许包含 `merchantId`、`cartItemIds` 或明细数组、`remark`、`contactPhone`、`fulfillmentType`。**价格、名称、库存一律由服务端从数据库读取**，任何来自客户端的金额字段都忽略。这是底线，否则接口会被人用两块钱买到十八块的饭。

`preflight` 单独存在的理由是：用户在结算页停留期间可能正好被买完或改价，让前端直接提交再失败重试的体验很差。

### 商家端

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/merchant/orders` | 接单台列表，`status` 分栏，带轮询游标 `afterId` |
| POST | `/api/merchant/orders/:orderNo/accept` | 接单 |
| POST | `/api/merchant/orders/:orderNo/start` | 开始制作 |
| POST | `/api/merchant/orders/:orderNo/ready` | 出餐，触发分配取餐码与通知 |
| POST | `/api/merchant/orders/:orderNo/verify` | 扫取餐码核销 |
| POST | `/api/merchant/orders/:orderNo/reject` | 拒单，必须给原因，走退款 |
| PATCH | `/api/merchant/dishes/:id/stock` | 改当日备货量 |
| PATCH | `/api/merchant/status` | 打烊与恢复 |

`ready` 与 `verify` 是两个真正需要事务的动作。`ready` 要同时分配取餐码、推进状态、把 `stock_locked` 转为 `stock_sold`、写站内信。`verify` 要核销并结束订单。

### 支付

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/payments` | 发起支付，请求体 `orderNo` 加 `channel` |
| GET | `/api/payments/:paymentNo` | 查支付态，前端轮询兜底 |
| POST | `/api/payments/callback/:channel` | 渠道异步回调，无鉴权但有验签 |
| POST | `/api/refunds` | 申请退款 |
| POST | `/api/refunds/:refundNo/audit` | 审核退款，商家或平台可操作 |

回调处理见 `docs/04` 第 3 节，是整个系统最容易写错的地方。

### 实时通道

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/events/stream` | SSE。学生端订阅自己的订单变更，商家端订阅本店新单 |

同一连接根据 token 里的角色决定推什么。商家端新单事件必须带 `orderId`，前端收到后主动拉取详情而不是依赖事件体，避免推送丢失导致状态不一致。

## 定时任务

| 频率 | 任务 | 说明 |
|---|---|---|
| 每 30 秒 | 支付超时兜底扫描 | 主路径是 Redis 延迟队列，这个是防止进程重启丢任务的兜底 |
| 每 60 秒 | 出餐超时未取检查 | `READY` 超过 `pickup_deadline_at` 自动置 `COMPLETED` |
| 每 10 分钟 | 日汇总增量 | 重算当日 `st_merchant_daily` 与 `st_dish_daily` |
| 每日 01:00 | 昨日全量汇总 | 回补前一日，回写 `m_dish.month_sold` |
| 每日 02:00 | 库存与购物车清理 | 建当日 `m_dish_stock`，清理超期购物车 |
| 每日 03:00 | 对账 | 拉渠道账单与 `p_payment` 比对，差异告警 |

定时任务在单体内用调度器实现，但必须考虑多实例重复执行。加 Redis 分布式锁，锁名带任务名与批次时间，超时时间小于执行周期。
