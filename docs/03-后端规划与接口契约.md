# 03 后端规划与接口契约

后端已实现：Spring Boot 3.2.5 / Java 17 / MyBatis-Plus / Flyway / JJWT，不引 Spring Security。本文是接口契约与实现口径的真源，`docs/04` 补充其中的难点实现细节。前端三端只发真实请求，契约改动以本文为准。

## 模块划分

单体，按业务域分包，模块之间通过 service 注入调用，禁止跨模块直接查表。代码在 `server/src/main/java/com/campus/smartorder/` 下：

user/                            收货地址、收藏、自提点
merchant/                        档口与菜单查询、商家控制台（订单操作、菜品管理、营业设置、报表）
cart/                            服务端购物车

数据库真源是 `db/schema.sql`，不走 ORM 反向生成。`V1__baseline.sql` 由 `scripts/gen-flyway.mjs` 从 schema.sql 生成，`V2`、`V3` 是手写增量；`pnpm run check:flyway` 逐字节比对防漂移，改库流程与迁移写法见 `docs/02`。

## 鉴权

两套主体，互不通用：`USER`（学生）与 `ACCOUNT`（商家 / 平台账号）。`JwtAuthenticationFilter` 解析 `Authorization: Bearer`，只认 `type=access` 的 JWT，把主体信息写进 request attribute，随后交给 `ConsoleAccess.enforce` 做路径级权限。白名单放行登录、注册、刷新、档口与菜单查询、健康检查、SSE 入口（SSE 在控制器内自行鉴权）。

学生端 access token 有效期 2 小时（`smartorder.security.access-token-ttl`），refresh token 有效期 30 天。refresh 是无状态 JWT 加库内摘要双保险：SHA-256 摘要落 `u_auth_token.token_hash`，每次刷新旧值作废、新值轮换入库，登出按摘要删行。这样登出、改密、封禁都能立即生效，纯无状态 JWT 做不到。

登录主入口是学号加密码，`POST /api/v1/auth/password/login` 与 `POST /api/v1/auth/register` 复用同一套双 token。哈希是 PBKDF2WithHmacSHA256 十二万轮，落库形态 `$pbkdf2-sha256$120000$<盐>$<摘要>`，盐与摘要各自 base64，参数写在串里而不是配置里，将来调轮数不需要迁移历史数据。没引 spring-security-crypto：只需要一个哈希算法时它带来的是一个依赖而不是能力，JDK 自带的 `SecretKeyFactory` 够用。比对走 `MessageDigest.isEqual`，不靠 `String.equals` 短路，否则错误密码在不同前缀长度上的耗时差会把学号枚举出来。`auth_source` 置 3 标记密码登录，接 CAS 当天按这个值把密码入口整体下线，不用逐个账号判断。种子账号的初始密码是学号后 6 位，写死在 `V2` 迁移里，只给开发环境用。另有一个纯字母演示账号 `admin` / `admin`，由 `V3` 迁移写入，供学生端本地联调，上线前删除或改密。

短信验证码登录已实现但是开发桩：`sendSmsCode` 固定生成 `000000` 落 `u_sms_code`（SHA-256 摘要、5 分钟过期），不接真实网关，也没有频控；`messaging.sms-enabled` 配置存在但无代码消费。CAS 未实现，过滤器白名单预留了 `/api/v1/auth/cas/` 前缀，api-client 留了 `casRedirect` / `casCallback` 的类型定义。接 CAS 时前端跳登录页、回跳带 `ticket`，后端拿 `ticket` 加自己的 `service` 地址回调 `serviceValidate`，解析学号与属性查 `u_campus_binding` 建或更新用户。属性字段名各校不一，映射表要写在配置里，这一步必须在学校测试环境验证。

学号密码登录要求 `student_no` 唯一，但短信登录隐式注册的访客没有学号。这一列早期是 `NOT NULL DEFAULT ''`，多个空值直接撞唯一索引，因此改成可空并把历史空串刷成 NULL——MySQL 的唯一索引不约束 NULL，一个用户表里可以有任意多个未绑定学号的访客。

商家与平台账号走 `sys_account` 用户名密码，`POST /api/v1/auth/console/login` 签发带 `subjectType=ACCOUNT`、`roleCode`、`merchantId` 声明的 JWT。种子账号的哈希是 `$argon2id$dev-placeholder` 占位符，`PasswordHasher` 遇到该前缀改与 `smartorder.security.dev-account-password` 明文比对，开发期统一密码 `demo123456`（`TODO(上线前)`）；真实哈希与学生同一套 PBKDF2。控制台的 refresh 是无状态 JWT，不落 `u_auth_token`——该表外键指向 `u_user`，账号主体塞不进去。

控制台权限在 `ConsoleAccess.enforce` 一处收口：`/api/v1/merchant/*` 要 ACCOUNT 主体加 `MERCHANT_` 前缀角色，其中 `MERCHANT_STAFF` 只放行 GET 和订单操作 POST（accept / start / ready / verify / reject），其余写操作 403；`/api/v1/platform/*` 仅 `PLATFORM_ADMIN`；退款审核仅 ACCOUNT 主体的 `MERCHANT_OWNER`，控制器以规范化路径复核，服务校验退款单与订单的档口归属。改角色或加接口时同步这里，别只改前端路由守卫。

## 接口契约

响应统一包装，`code` 为 0 表示成功，非 0 是业务错误码，集中在 `common/api/ErrorCode.java`。HTTP 状态码只表达传输层结果，业务失败一律 200 加非零 `code`，避免前端在拦截器里做双重判断。

```
{ "code": 0, "message": "ok", "data": { }, "traceId": "..." }
```

分页统一 `page` 从 1 起、`pageSize` 默认 10、上限 200（`PaginationInnerInterceptor` 的 `maxLimit`），返回 `{ list, total, page, pageSize }`。列表一律倒序按 `id`，不按 `created_at`，因为同秒并发写入时排序不稳定会导致翻页重复或漏项。

标量类型有两条硬约定。所有 `BIGINT` 主外键序列化成字符串，由 `JacksonConfig` 给 `Long` 注册 `ToStringSerializer` 全局生效，前端不参与 ID 运算、只做等值比较与回传；数字照常输出会有真实代价，`order_id` 超过 2^53 后 `JSON.parse` 会静默改变取值，这种错在页面上看不出来。所有时间统一带偏移的 ISO-8601，例如 `2026-11-16T12:13:31.727+08:00`。库里存的是 `DATETIME(3)` 墙上时间，JDBC 连接强制会话时区 `+08:00`，出口由序列化器按 `smartorder.zone-id` 补上偏移。裸的 `2026-11-16T12:13:31.727` 会被浏览器按访问者本地时区解析，运营人员和学生在同一套系统里会看到不同的时间；带偏移则不存在这个歧义，而 `Zulu` 或毫秒时间戳又让日志对不齐。反序列化两种都收，偏移形式先换算到 `zone-id` 再入库，本地形式按墙上时间直接采用，方便管理后台手填。

`PATCH /merchant/status` 请求体为 `{ closed: boolean, reason?: string }`，返回重新计算后的档口资料；商家账号不能借此修改平台审核或封禁状态。

- `closed=true`：将服务器时区当天的 `m_date_override` 写为 `CLOSED`，立即暂停接单；原因为空时用「临时歇业」，去除首尾空白后最多 128 字。
- `closed=false`：将当天记录写为 `OPEN`，立即恢复营业，即使当前已过打烊时间、当日休息或尚未设置每周时段也能营业；不是仅删除歇业记录。仅平台状态为正常营业（`status=1`）的档口可执行，其他状态返回 `30002` 并提示联系平台。
- 每个档口每天只有一条覆盖记录，手动开关会替换当天原有的 `CLOSED` / `HOURS` / `OPEN`，并清空覆盖时段及不再适用的歇业原因，不改每周计划。记录仅在对应 `biz_date` 生效，次日零点恢复新一天的计划或覆盖；当天可再次临时歇业，或通过删除当天调整恢复按计划营业。
- `OPEN` 的有效状态为 `open=true`、`closedToday=false`、`closeReason=""`，营业及接单起止时间均返回 `00:00`，表示当日全天、到次日零点结束。学生端与控制台共用该营业判定，仍受档口平台状态、菜品及库存等业务条件约束。
- `GET /merchant/hours` 的覆盖记录类型包含 `OPEN`，控制台显示为「临时营业 / 当日有效」；`PUT /merchant/hours/override` 仍只接受 `CLOSED`、`HOURS`，`OPEN` 由手动恢复营业写入。

`ready` 与 `verify` 是两个真正需要事务的动作。`ready` 要同时分配取餐码、推进状态、把 `stock_locked` 转为 `stock_sold`、写站内信。`verify` 要核销并结束订单。

报表全部从 `o_order`、`o_order_item`、`o_refund` 现聚合，`st_merchant_daily` / `st_dish_daily` 只是历史落表预留，不是读取源。金额口径：流水 = 已支付且非 `CLOSED` / `CANCELLED` 的订单实付之和，净额 = 流水 - 已退款。daily 序列升序补零返回，前端 StatsView 的「对比昨日」依赖这个顺序。

### 支付与退款

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/payments` | 发起支付，body `orderNo` 加 `channel`，`paymentNo = "P" + orderNo` 复用 |
| POST | `/payments/{paymentNo}/confirm` | MOCK 渠道确认，校验支付单归属当前用户，越权报 `PAYMENT_NOT_FOUND` |
| GET | `/payments/{paymentNo}` | 查支付态，前端轮询兜底 |

支付后在 `USER_CANCEL_WINDOW_SECONDS`（种子 180 秒）窗口内自助取消，会即时生成 `SUCCEEDED` 退款单（MOCK 无真实资金动作）。`/refunds/{refundNo}/audit` 已接入商家历史订单页，仅 `MERCHANT_OWNER` 可审核本店 `PENDING` 申请：同意时校验成功的 MOCK 支付与整单金额，置订单 `REFUNDED`、释放库存和券；驳回须填写原因，并按最近一条进入 `REFUNDING` 的日志恢复 `PAID` / `ACCEPTED` / `COOKING`，不释放资源。审核采用行锁、订单 CAS 和事务，同一结论重试返回原结果，相反结论拒绝。待审申请须保留原库存与券占用，并有完整的退款前状态日志。**学生退款申请接口 `/refunds` 仍未实现**；商家拒单当前只置 `REJECTED` 并释放库存，不建退款单。真实渠道退款、部分退款和回调仍待接入。

领券 / 发券接口没有，券由种子与迁移发放；下单用券走 `MarketingService`（满减 / 折扣 / 运费券，门槛、档口范围、封顶校验），取消与超时关单都还券。商家回复评价没有接口，`reply_content` 恒空。评价后加权回写 `m_merchant.rating_score`（百分制）与 `rating_count`。

### 实时通道

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/events/stream` | SSE。token 走 `?token=` 查询参数，也认 `Authorization` 头 |

同一连接根据 token 主体决定推什么：`USER` 订个人订单变更（事件名 `order`），`ACCOUNT` 按 `merchantId` 订本店新单与状态变化（事件名 `merchant_order`）。事件体带 `orderNo`、`merchantId`、`status`、`serverTime`，前端收到后主动拉详情而不是依赖事件体，避免推送丢失导致状态不一致。

推送有两条路：业务操作后即时 publish；兜底每 3 秒扫 `o_order.updated_at`（回看 15 秒、限 200 行），与内存里的上次状态比对去重。心跳 `ping` 每 20 秒一次，emitter 存活 15 分钟，超时即完成、由客户端重连。服务端没有 `Last-Event-ID` 补发机制，重连后前端全量重拉。

## 定时任务

| 频率 | 任务 | 说明 |
|---|---|---|
| 每 60 秒 | 支付超时关单 | `status='PENDING_PAYMENT' AND expire_at < now`，CAS 置 `CLOSED`，释放库存与券 |
| 每 60 秒 | 取餐超时自动完成 | `READY` 且 `pickup_deadline_at` 已过，CAS 置 `COMPLETED` |
| 每 3 秒 | SSE 兜底扫描 | 见实时通道一节 |
| 每 20 秒 | SSE 心跳 | 向所有 emitter 发 `ping` |

调度池大小 2，单实例部署。日汇总回写、对账、每日库存初始化任务未实现；`ORDER_AUTO_COMPLETE_MINUTES` 配置存在但未被消费，自动完成实际由 `pickup_deadline_at`（出餐 + `pickup-hold-minutes`，默认 45 分钟）驱动。引入 Redis 延迟队列与多实例部署时，任务要加分布式锁，锁名带任务名与批次时间，超时时间小于执行周期——当前没有 Redis，也不支持多实例。

## 实现口径与预留项

MSW 模拟层已整体删除，三端直连真实后端，不再有「模拟层与后端差异」的问题。早期对着模拟层定下的行为口径全部保留在后端实现里：

| 位置 | 口径 |
|---|---|
| `fulfillmentType` | 落 `o_order.fulfillment_type`，详情与列表回读同一个值 |
| 自助取消窗口 | 读 `sys_config.USER_CANCEL_WINDOW_SECONDS`，下单校验与详情展示用同一个取值函数 |
| 取消与超时关闭 | 未支付主动取消、支付后自助取消、支付超时自动关闭三条路径都把券退回 `UNUSED` 并释放当日库存锁 |
| 重复下单 | 前端带 `clientOrderNo`，先按 `(user_id, client_order_no)` 回查命中即回放原单，唯一索引兜底 |
| 订单 `version` | 插入即置 1，与乐观锁首次更新后的语义对齐 |
| 通知已读 | 更新条件带 `user_id` 与 `read_at IS NULL` |
| 匿名评价 | 昵称换「匿名用户」，头像照常返回 |
| 行级 `discountAmount` | 恒为 0，优惠只记订单级 |
| `minBuyCount` | 字段有值但不拦 |

后两条不是「决定不实现」，是价格与优惠模型还没定稿：行级优惠要先把单品券、档位折扣与满减的分摊顺序钉死，`minBuyCount` 要先明确它是规格组起订量还是整份菜起订量。留一个可见的空缺比造一个看起来对的实现更容易被及时发现。
