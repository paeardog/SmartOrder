# 04 订单状态机与并发难点

前面三份是骨架，这一份是真正决定这个系统能不能上线运营的部分。校园点单的难点不在功能多，在于高峰期大量用户同时抢有限的出餐能力，任何一处判断失误都会变成食堂门口的争执。

## 1 状态机

### 状态与合法转移

| 当前 | 可转移到 | 触发者 | 前置条件 | 副作用 |
|---|---|---|---|---|
| `PENDING_PAYMENT` | `PAID` | 支付确认 / 渠道回调 | 验签通过且金额一致 | 分配取餐时段，库存 `locked` 保持 |
| `PENDING_PAYMENT` | `CANCELLED` | 用户 | 未支付 | 释放 `locked`，还券 |
| `PENDING_PAYMENT` | `CLOSED` | 系统 | 超过 `expire_at` | 释放 `locked`，还券 |
| `PAID` | `ACCEPTED` | 商家 | 档口营业中 | 计算 `expect_take_at` |
| `PAID` | `REJECTED` | 商家 | 必须给原因 | 释放库存；真实渠道接入后生成退款单 |
| `PAID` | `REFUNDING` | 用户 | 在自助取消窗口内直接退，超窗走审核 | 生成退款单 |
| `ACCEPTED` | `COOKING` | 商家 | — | — |
| `ACCEPTED` / `COOKING` | `READY` | 商家 | 分配 `pickup_code` | 通知用户，`locked` 转 `sold` |
| `READY` | `COMPLETED` | 商家核销 或 系统超时 | 取餐码匹配 | 订单结束，计入统计 |
| `REJECTED` | `REFUNDING` | 系统 | 拒单退款 | 生成退款单 |
| `REFUNDING` | `REFUNDED` | 渠道退款成功 | — | 回写统计净额 |
| `REFUNDING` | 原状态 | 审核驳回 | — | 记日志，不改业务态 |

终态：`COMPLETED`、`CANCELLED`、`CLOSED`、`REFUNDED`。终态不接受任何转移。

实现里 `PAID` / `ACCEPTED` / `COOKING` 三态都可以被商家拒单（`casReject` 的前态是三者之一），自助取消当前走「窗口内即时退款」直接置 `CANCELLED` 并写 `SUCCEEDED` 退款单。退款审核已接入：事务内锁定退款单和订单，同意只支持 MOCK 整单退款并释放库存与券，驳回按进入 `REFUNDING` 的日志恢复原状态。同一审核结论重复提交不再修改资源。待审期间保留原库存与券占用；学生退款申请、拒单建退款单和真实渠道退款仍未实现，见 `docs/03` 的预留项清单。

`REJECTED` 与 `CANCELLED` 分开是有意的。前者是商家缺货拒单，会拉低该档口的拒单率指标，需要被统计和考核；后者是用户自己的决定，影响的是用户信用分。混成一个状态，运营就没法区分「这家店不行」和「这家用户不行」。

### 实现：转移表加 CAS

状态判定收在 `order/domain/OrderStateMachine.java`：静态 `EnumMap<OrderStatus, Set<OrderStatus>>` 转移表，`require(from, to)` 非法即抛 `IllegalTransitionException`，`stockEffect(from, to)` 给出这次流转该对库存做什么（不动 / 加锁 / 释放 / 锁转售出）。任何直接 `UPDATE o_order SET status` 的代码都不许出现。

落库是 `order/mapper/OrderMapper.java` 里一组条件 UPDATE，每个动作一条，前态写死在 WHERE 里：

```java
@Update("""
        UPDATE o_order
           SET status = 'ACCEPTED', accepted_at = NOW(3), expect_take_at = #{expectTakeAt}, version = version + 1
         WHERE id = #{orderId} AND status = 'PAID'
        """)
int casAccept(@Param("orderId") Long orderId, @Param("expectTakeAt") LocalDateTime expectTakeAt);
```

`WHERE status = 'PAID'` 这一句是整个方案的关键。数据库行锁保证同一行上只有一个事务能更新成功，其余返回影响行数 0，service 层复查当前状态后抛 `ORDER_CONCURRENT_MODIFIED` 或 `ORDER_STATUS_ILLEGAL`。这样即便用户连点两次接单、或者接单请求与超时取消请求同时到达，也只有一次生效。

写日志和改状态必须在同一个事务里。日志插入失败要回滚状态变更，否则出问题时无从追查。

`version` 列在状态流转路径下不是必需的，状态本身就是天然的乐观锁版本，每条 CAS 都顺带 `version + 1`。真正消费它的是 `casUpdateExpectTakeAt`：不改变状态只改预计取餐时间，WHERE 里额外带 `AND version = #{version}`。

## 2 下单主流程

事务边界要尽量小，但价格计算、库存扣减、订单落库必须原子。

```
1  校验：用户认证态、档口营业态、菜品上架态、限购数量
2  重算价格：全部取数据库当前值，丢弃客户端传入的任何金额
3  规格校验：每个必选组已选、选择数在 [min_select, max_select] 内、加料库存够
4  用券校验：门槛、档口范围、封顶，券核销（UNUSED → USED 条件更新）在事务内
5  开事务
6    扣库存（见第 5 节）
7    INSERT o_order 与 o_order_item
8    INSERT o_order_status_log 初始态
9  提交事务
10 事务外：清购物车、推 SSE
```

第 10 步必须在事务外。如果放在事务内，事务回滚了推送却已经发出去；如果推送失败整个下单也跟着失败，用户体验被无关依赖绑架。SSE 推送丢失由每 3 秒的兜底扫描补上（`docs/03` 实时通道一节）。当前没有延迟队列，支付超时关单完全靠定时扫描，见第 4 节。

### 幂等

`X-Client-Order-No` 由前端在点击进入结算页时生成一次 UUID，提交时带上，网络重试复用同一个值。数据库上 `UNIQUE (user_id, client_order_no)` 兜底。

冲突时不能直接报失败。正确行为是捕获重复键异常后按 `(user_id, client_order_no)` 回查原订单并返回，让前端认为成功。用户看到「下单失败」但实际上单成功了，是这类系统最恶劣的 bug，会直接导致重复购买。

## 3 支付回调

本节是接入真实渠道时的施工契约。当前只有 MOCK 渠道：`POST /api/v1/payments/{paymentNo}/confirm` 由前端主动调用，已实现归属校验、幂等（已 SUCCESS 直接返回）、订单已关闭 / 已取消 / 已过期则置支付失败、`casMarkSuccess` 加 `casMarkPaid` 两级 CAS、成功后写取餐计划。MOCK 没有真实资金，「钱收了但订单关了」的自动退款分支无从触发，接真实渠道时必须按下面的顺序补齐，回调入口与 `p_callback_log` 都已预留。

回调是全系统风险最高的入口：无鉴权、可重放、可能乱序、可能丢失。处理顺序固定，一步都不能省。

```
1  收到请求，立刻原样写入 p_callback_log（含 raw_body、headers、IP、验签结果）
2  验签失败 → 记录 handled=3，应答 400，结束。绝不改任何业务状态
3  按 payment_no 查 p_payment
4  已是 SUCCESS → handled=2 幂等丢弃，应答 200
5  校验金额：回调金额 != pay_amount → 告警并返回失败，不动状态
6  校验订单：订单已 CLOSED 或 CANCELLED → 走自动退款分支，不动成 PAID
7  CAS 更新 p_payment PENDING → SUCCESS，写 channel_txn_no 与 paid_at
8  若第 7 步影响行数为 0 → 并发已处理，幂等返回成功
9  CAS 置订单 PAID（casMarkPaid），写取餐计划
10 应答渠道成功格式
```

第 1 步先落日志再处理，是为了保证任何回调都不丢。渠道的失败重试机制很粗暴，处理到第 9 步时如果进程崩了，至少原始报文在库里，人工补偿有据可依。

第 6 步是最容易漏的竞态：用户下单后超时被系统关闭，紧接着支付回调到达。此时钱收了但订单已经关了。必须自动发起退款，而不是简单拒绝或强行改成已支付。这条分支要单独写测试用例。

`channel_txn_no` 参与幂等判断。渠道有时会用不同的商户订单号重发同一笔成功通知，只按 `payment_no` 判重会漏。

前端轮询 `GET /api/v1/payments/{paymentNo}` 是兜底，不依赖回调一定到达。回调和轮询走同一个「置为已支付」函数，保证行为一致。

## 4 支付超时取消

当前实现只有一条路：定时扫表。`OrderScheduledService.autoCloseExpiredOrders` 每 60 秒查一次「状态仍是待支付且已过期」的订单（`idx_o_timeout (status, expire_at)`，每批 100 条），逐单 `casClose` 置 `CLOSED`、释放库存与券、写状态日志。过期时长读 `sys_config.ORDER_PAY_TIMEOUT_SECONDS`（种子 900 秒）。校园量级下 60 秒的关闭延迟可以接受，扫描本身幂等，进程重启不丢任务。

Redis 有序队列是二期优化，只有当扫描延迟或数据库压力被监控证明是问题时才上：

```
下单成功 → ZADD order:expire <expireTimestamp> <orderId>
消费循环 → ZRANGEBYSCORE order:expire 0 <now> LIMIT 0 100
           对每个 orderId：ZREM 返回 1 才处理，返回 0 说明已被别处取走
处理 → 查订单，若仍是 PENDING_PAYMENT 且已过 expire_at → casClose，释放库存
```

`ZREM` 的返回值是分布式下的领取令牌，返回 1 表示当前实例抢到了处理权。这比加分布式锁简单，效果相同。引入后扫表降级为兜底，两者都必须是幂等的。不用 RabbitMQ 死信队列：多维护一个中间件，对单体的校园项目收益不抵成本。

用户主动支付和超时关闭可能同时发生。支付路径在 `casMarkPaid` 前会重新读一次订单状态，若已 `CLOSED` 则拒绝支付并提示重新下单；关闭路径靠 `WHERE status = 'PENDING_PAYMENT'` 保证不会关掉刚支付成功的单子。谁先提交谁赢，输的一方看到影响行数 0 后走各自的补偿分支。

## 5 防超卖

分两个阶段演进，不要一上来就上 Redis。阶段一已实现，阶段二未引入。

### 阶段一：数据库乐观锁

```sql
UPDATE m_dish_stock
   SET stock_locked = stock_locked + 2
 WHERE dish_id = 1 AND biz_date = CURDATE()
   AND stock_total >= stock_locked + stock_sold + 2;
```

判断影响行数，为 0 即库存不足，抛业务异常回滚整个下单事务。

条件写成加法而不是 `stock_total - stock_locked - stock_sold >= 2`，有两个实测原因。三个 `stock_*` 列都是 `INT UNSIGNED`，减法形式在不变量被破坏时会抛 `ERROR 1690 BIGINT UNSIGNED value is out of range`，一条本该返回零行的查询变成异常；加法形式在正常情况下与减法形式完全等价，异常情况下只是不命中行，让守卫语句自己永远不可能失败。释放库存同理必须带 `AND stock_locked >= :n`，实测无符号列会把越界的重复释放直接拒掉，这是最后一道兜底。

正确性由数据库行锁保证，没有缓存与数据库不一致的风险，实现不到二十行。代价是同一菜品的并发下单会串行排队。

先量一下上限：单个菜品在一分钟内被下单的次数，现实中很难超过两三百。InnoDB 行锁的吞吐远高于这个数。所以阶段一在校园场景下大概率够用，**先上线，用监控数据决定是否要优化**，不要凭想象提前复杂化。

`m_dish_option.stock`（加料库存）同样用这条语句扣，在同一个事务内。

### 阶段二：Redis 预扣

只有当压测或线上监控证明行锁确实是瓶颈时才做。

```
运营设置备货量时 → SET stock:{dishId}:{date} <可用数>
下单 → Lua 脚本原子地 判断余量 + DECR + 记录流水
      返回 -1 表示不足，直接拒绝，不碰数据库
      返回扣减成功 → 进入数据库事务写订单（事务里仍执行阶段一的 SQL 作为最终防线）
取消或超时 → Lua 脚本 INCR 回补
对账 → 每分钟比对 Redis 余量与 total-locked-sold，偏差超阈值告警并以数据库为准重建
```

关键点：Redis 只做流量拦截，数据库那一步的乐观锁不删。Redis 和 MySQL 是两个独立系统，不存在跨系统事务，任何"以 Redis 为准"的设计都会在故障时超卖。多一层数据库校验，最坏情况是少卖，不会超卖。

Lua 脚本必须整体原子，判断和扣减不能分两次调用。

## 6 取餐码与核销

`READY` 时分配，不在下单时分配。未支付的订单占着码位没有意义，还会让用户误以为可以直接去取。

```
生成：查当日该档口已发码数（COUNT DISTINCT pickup_code），从 数+1 起顺序取，
     %04d 格式化成四位数字（0001 起），先查占用、被占则递增重试，最多 8 次，
     超过 9999 或重试耗尽抛 PICKUP_CODE_UNAVAILABLE，uk_o_pickup_code 是并发下的最后防线
核销：商家端扫码或手输 → 按 orderNo 定位订单（限定本店），比对 pickupCode，
      不符报 PICKUP_CODE_INVALID，不透露订单是否存在
      UPDATE o_order SET status='COMPLETED', taken_at=NOW(3), finished_at=NOW(3)
       WHERE id=? AND status='READY'
      影响行数 0 → 复查状态，报并发冲突或状态不符
```

顺序码而不是随机码：四位顺序号让学生和店员都好念好记，撞码只可能是并发生成，占用预检加唯一索引兜住。限定 `biz_date` 与 `merchant_id` 是为了防跨天撞码，也避免把别家档口的订单核销掉；按码查单的 `GET /merchant/pickup` 同样带这两个限定。码位不回收——取消订单占用的当天编号不重新发放，四位数字有一万种组合，单日单档口不可能用完。

自动完成兜底：出餐后超过 `pickup_deadline_at` 没人取，定时任务每 60 秒从 `READY` 推到 `COMPLETED`。deadline 在出餐时写死为 `ready_at + pickup-hold-minutes`（默认 45 分钟）。不这么做的话，学生忘了取餐、档口不会每天去打码核销积压订单，商家报表会永久挂着几十个未完成单，营业额就对不上。`sys_config.ORDER_AUTO_COMPLETE_MINUTES` 是早期设计留下的键，当前未被消费，改保留时长要改 `smartorder.order.pickup-hold-minutes`。

## 7 午高峰

真正会打挂系统的是 11:30 到 12:10 的读流量，不是写流量。

当前实现没有缓存，菜单与档口列表每次直查库，靠覆盖索引撑。下面的缓存与限流是上线放量前的优化项，不是已落地的能力：

`GET /merchants/{merchantId}/menu` 结果进 Redis，TTL 30 秒，key 含 `stockVersion`（返回体里已有这个字段，就是为缓存失效准备的）。商家改价、下架、调库存时主动删 key。30 秒的库存延迟可以接受，因为最终扣减仍在数据库层做严格校验，缓存只影响"看起来还有"到"下单被拒"的反应速度。

档口列表缓存 60 秒。菜品图片走对象存储加 CDN，绝不让图片流量经过应用进程。

限流分三层：网关按 IP，应用按用户，下单接口按用户加档口。`POST /orders` 单用户 3 秒 1 次，超了返回 `RATE_LIMITED`。这一层防的是前端按钮被连点，也防脚本刷单。当前后端没有任何限流实现，错误码已定义但无抛出点，前端靠提交锁与节流兜底；短信网关接入前必须先补验证码频控，否则 `000000` 开发桩换成真实短信的那天就是被刷的那天。

连接池按 2 核机器配，Hikari 最大连接数不超过 50。默认值在大内存机器上调小了会明显感觉排队，调大了会把 MySQL 拖垮，两者都要监控等待时长。

## 8 金额一致性

三处必须恒等，任何一处对不上就是 bug：

```
明细行：line_amount = unit_price × quantity + pack_fee - discount_amount
订单头：item_amount = Σ(unit_price × quantity)
        pack_fee    = Σ line.pack_fee
        pay_amount  = item_amount + pack_fee + delivery_fee - discount_amount
        恒等于        Σ line_amount + delivery_fee
支付：  SUCCESS 的 p_payment.pay_amount = o_order.pay_amount
退款：  Σ o_refund.refund_amount(status=SUCCEEDED) <= o_order.pay_amount
```

`scripts/check-schema.mjs` 已经把前三条实现对种子数据做检查，首次运行就抓出十四条金额错误和三条规格项张冠李戴。同一套断言应该在后端做成单元测试和每日对账任务，而不只是脚本。

优惠分摊的尾差处理要固定：按比例分摊时，最后一行用「总额减去前面各行之和」倒推，避免浮点或取整累加导致合计对不上。系统里金额全是整数分，取整用向下取整，尾差归入最后一行。

## 9 幂等清单

需要幂等保护的入口，逐个确认：

| 入口 | 幂等键 | 存储位置 |
|---|---|---|
| 下单 | `user_id` + `client_order_no`，命中回查直接回放原单 | `uk_o_client_order` 唯一索引 |
| 发起支付 | `paymentNo = "P" + orderNo` 复用，同一订单只有一个支付单 | `uk_p_payment_no` |
| 支付确认 / 回调 | `payment_no` 状态 CAS，已 SUCCESS 直接返回 | `p_payment.status` |
| 退款回调 | `refund_no` 加 `channel_refund_no`（未接入，契约预留） | `uk_o_refund_no` |
| 商家接单 | `order_id` 加 `from_status` CAS | `o_order.status` |
| 核销 | `order_id` 加 `status='READY'` CAS | 同上 |
| SSE 重连 | 无 `lastEventId` 补发；客户端指数退避重连后全量重拉，服务端 3 秒兜底扫描补推送 | `o_order.updated_at` |

`p_callback_log` 上刻意没有唯一索引。同一笔交易渠道可能通知多次，日志要全留，幂等在 `p_payment` 的状态上判断。
