# 04 订单状态机与并发难点

前面三份是骨架，这一份是真正决定这个系统能不能上线运营的部分。校园点单的难点不在功能多，在于高峰期大量用户同时抢有限的出餐能力，任何一处判断失误都会变成食堂门口的争执。

## 1 状态机

### 状态与合法转移

| 当前 | 可转移到 | 触发者 | 前置条件 | 副作用 |
|---|---|---|---|---|
| `PENDING_PAYMENT` | `PAID` | 渠道回调 | 验签通过且金额一致 | 分配取餐时段，库存 `locked` 保持 |
| `PENDING_PAYMENT` | `CANCELLED` | 用户 | 未支付 | 释放 `locked` |
| `PENDING_PAYMENT` | `CLOSED` | 系统 | 超过 `expire_at` | 释放 `locked` |
| `PAID` | `ACCEPTED` | 商家 | 档口营业中 | 计算 `expect_take_at` |
| `PAID` | `REJECTED` | 商家 | 必须给原因 | 生成退款单 |
| `PAID` | `REFUNDING` | 用户 | 在自助取消窗口内直接退，超窗走审核 | 生成退款单 |
| `ACCEPTED` | `COOKING` | 商家 | — | — |
| `ACCEPTED` / `COOKING` | `READY` | 商家 | 分配 `pickup_code` | 通知用户，`locked` 转 `sold` |
| `READY` | `COMPLETED` | 商家核销 或 系统超时 | 取餐码匹配 | 订单结束，计入统计 |
| `REFUNDING` | `REFUNDED` | 渠道退款成功 | — | 回写统计净额 |
| `REFUNDING` | 原状态 | 审核驳回 | — | 记日志，不改业务态 |

终态：`COMPLETED`、`CANCELLED`、`CLOSED`、`REFUNDED`。终态不接受任何转移。

`REJECTED` 与 `CANCELLED` 分开是有意的。前者是商家缺货拒单，会拉低该档口的拒单率指标，需要被统计和考核；后者是用户自己的决定，影响的是用户信用分。混成一个状态，运营就没法区分「这家店不行」和「这家用户不行」。

### 实现：转移表加 CAS

状态判定只允许通过一个函数，任何直接 `UPDATE o_order SET status` 的代码都不许出现。

```ts
const TRANSITIONS: Record<string, string[]> = {
  PENDING_PAYMENT: ['PAID', 'CANCELLED', 'CLOSED'],
  PAID: ['ACCEPTED', 'REJECTED', 'REFUNDING'],
  ACCEPTED: ['COOKING', 'READY', 'REFUNDING'],
  COOKING: ['READY', 'REFUNDING'],
  READY: ['COMPLETED'],
  REFUNDING: ['REFUNDED', 'PAID', 'ACCEPTED'],
  COMPLETED: [], CANCELLED: [], CLOSED: [], REJECTED: [], REFUNDED: [],
};

export async function transit(
  orderId: bigint,
  from: OrderStatus,
  to: OrderStatus,
  operator: { type: 'USER' | 'MERCHANT' | 'PLATFORM' | 'SYSTEM'; id?: bigint; name?: string },
  patch: Record<string, unknown> = {},
  note = '',
) {
  if (!TRANSITIONS[from]?.includes(to)) {
    throw new IllegalTransitionError(from, to);
  }
  const { count } = await prisma.$executeRaw`
    UPDATE o_order SET status = ${to}, version = version + 1,
      ${Prisma.raw(buildSet(patch))}
    WHERE id = ${orderId} AND status = ${from}`;
  if (count !== 1) {
    throw new ConcurrentModifiedError(orderId);
  }
  await prisma.o_order_status_log.create({
    data: { orderId, fromStatus: from, toStatus: to, ...operator, note },
  });
}
```

`WHERE status = ${from}` 这一句是整个方案的关键。数据库行锁保证同一行上只有一个事务能更新成功，其余返回 `count = 0` 并抛出冲突异常。这样即便用户连点两次接单、或者接单请求与超时取消请求同时到达，也只有一次生效。

写日志和改状态必须在同一个事务里。日志插入失败要回滚状态变更，否则出问题时无从追查。

`version` 列在正常路径下不是必需的，状态本身就是天然的乐观锁版本。留着是为了处理那种不改变状态但要改其他字段的更新，例如商家修改 `expect_take_at`。

## 2 下单主流程

事务边界要尽量小，但价格计算、库存扣减、订单落库必须原子。

```
1  校验：用户认证态、档口营业态、菜品上架态、限购数量
2  重算价格：全部取数据库当前值，丢弃客户端传入的任何金额
3  规格校验：每个必选组已选、选择数在 [min_select, max_select] 内、加料库存够
4  开事务
5    扣库存（见第 5 节）
6    INSERT o_order 与 o_order_item
7    INSERT o_order_status_log 初始态
8  提交事务
9  事务外：投递延迟队列消息、清购物车、推 SSE
```

第 9 步必须在事务外。如果放在事务内，事务回滚了消息却已经发出去；如果消息投递失败整个下单也跟着失败，用户体验被无关依赖绑架。投递失败记入重试表即可，兜底扫描任务会补上。

### 幂等

`X-Client-Order-No` 由前端在点击进入结算页时生成一次 UUID，提交时带上，网络重试复用同一个值。数据库上 `UNIQUE (user_id, client_order_no)` 兜底。

冲突时不能直接报失败。正确行为是捕获重复键异常后按 `(user_id, client_order_no)` 回查原订单并返回，让前端认为成功。用户看到「下单失败」但实际上单成功了，是这类系统最恶劣的 bug，会直接导致重复购买。

## 3 支付回调

回调是全系统风险最高的入口：无鉴权、可重放、可能乱序、可能丢失。处理顺序固定，一步都不能省。

```
1  收到请求，立刻原样写入 p_callback_log（含 raw_body、headers、IP、验签结果）
2  验签失败 → 记录 handled=3，应答 400，结束。绝不改任何业务状态
3  按 payment_no 查 p_payment
4  已是 SUCCESS → handled=2 幂等丢弃，应答 200
5  校验金额：回调金额 != pay_amount → 告警并返回失败，不动状态
6  校验订单：订单已 CLOSED 或 CANCELLED → 走自动退款分支，不动成 PAID
7  CAS 更新 p_payment PENDING → SUCCESS，写 channel_txn_no 与 paid_at
8  若第 7 步影响行数为 0 → 并发已处理，幂等返回成功
9  transit(orderId, PENDING_PAYMENT, PAID)
10 应答渠道成功格式
```

第 1 步先落日志再处理，是为了保证任何回调都不丢。渠道的失败重试机制很粗暴，处理到第 9 步时如果进程崩了，至少原始报文在库里，人工补偿有据可依。

第 6 步是最容易漏的竞态：用户下单后超时被系统关闭，紧接着支付回调到达。此时钱收了但订单已经关了。必须自动发起退款，而不是简单拒绝或强行改成已支付。这条分支要单独写测试用例。

`channel_txn_no` 参与幂等判断。渠道有时会用不同的商户订单号重发同一笔成功通知，只按 `payment_no` 判重会漏。

前端轮询 `GET /api/payments/:paymentNo` 是兜底，不依赖回调一定到达。回调和轮询走同一个「置为已支付」函数，保证行为一致。

## 4 支付超时取消

主路径用 Redis 有序队列，不用轮询扫表，也不用 RabbitMQ 死信队列。

```
下单成功 → ZADD order:expire <expireTimestamp> <orderId>
消费循环 → ZRANGEBYSCORE order:expire 0 <now> LIMIT 0 100
           对每个 orderId：ZREM 返回 1 才处理，返回 0 说明已被别处取走
处理 → 查订单，若仍是 PENDING_PAYMENT 且已过 expire_at → transit 到 CLOSED，释放库存
```

`ZREM` 的返回值是分布式下的领取令牌，返回 1 表示当前实例抢到了处理权。这比加分布式锁简单，效果相同。

轮询扫表在数据量增长后会退化成全表扫描，而且延迟等于轮询间隔。引入 RabbitMQ 意味着多维护一个中间件，对单体的校园项目收益不抵成本。

`idx_o_timeout (status, expire_at)` 服务于**兜底扫描**：每 30 秒查一次「状态仍是待支付且已过期」的订单，把因为进程重启、Redis 丢数据、消息处理异常而漏掉的单子捞回来。延迟队列负责快，兜底扫描负责准。两者都存在，且都必须是幂等的。

用户主动支付和超时关闭可能同时发生。支付路径在 `transit` 前会重新读一次订单状态，若已 `CLOSED` 则拒绝支付并提示重新下单；关闭路径靠 `WHERE status = 'PENDING_PAYMENT'` 保证不会关掉刚支付成功的单子。谁先提交谁赢，输的一方看到 `count = 0` 后走各自的补偿分支。

## 5 防超卖

分两个阶段演进，不要一上来就上 Redis。

### 阶段一：数据库乐观锁

```sql
UPDATE m_dish_stock
   SET stock_locked = stock_locked + 2
 WHERE dish_id = 1 AND biz_date = CURDATE()
   AND stock_total >= stock_locked + stock_sold + 2;
```

判断影响行数，为 0 即库存不足，抛业务异常回滚整个下单事务。

条件写成加法而不是 `stock_total - stock_locked - stock_sold >= 2`，有两个实测原因。三个 `stock_*` 列都是 `INT UNSIGNED`，减法形式在不变量被破坏时会抛 `ERROR 1690 BIGINT UNSIGNED value is out of range`，一条本该返回零行的查询变成异常；加法形式在正常情况下与减法形式完全等价，异常情况下只是不命中行，让守卫语句自己永远不可能失败。释放库存同理必须带 `AND stock_locked >= :n`，实测无符号列会把越界的重复释放直接拒掉，这是最后一道兜底。

正确性由数据库行锁保证，没有缓存与数据库不一致的风险，实现不到二十行。代价是同一菜品的并发下单会串行排队。

先量一下上限：单个菜品在一分钟内被下单的次数，现实中很难超过两三百。InnoDB 行锁的吞吐远高于这个数。所以阶段一在校园场景下大概率够用，**先上线，用监控数据决定是否要优化**，不要凭想象提前复杂化。

`m_dish_option.stock`（加料库存）同样用这条语句扣，在同一个事务内。

### 阶段二：Redis 预扣

只有当压测或线上监控证明行锁确实是瓶颈时才做。

```
运营设置备货量时 → SET stock:{dishId}:{date} <可用数>
下单 → Lua 脚本原子地 判断余量 + DECR + 记录流水
      返回 -1 表示不足，直接拒绝，不碰数据库
      返回扣减成功 → 进入数据库事务写订单（事务里仍执行阶段一的 SQL 作为最终防线）
取消或超时 → Lua 脚本 INCR 回补
对账 → 每分钟比对 Redis 余量与 total-locked-sold，偏差超阈值告警并以数据库为准重建
```

关键点：Redis 只做流量拦截，数据库那一步的乐观锁不删。Redis 和 MySQL 是两个独立系统，不存在跨系统事务，任何"以 Redis 为准"的设计都会在故障时超卖。多一层数据库校验，最坏情况是少卖，不会超卖。

Lua 脚本必须整体原子，判断和扣减不能分两次调用。

## 6 取餐码与核销

`READY` 时分配，不在下单时分配。未支付的订单占着码位没有意义，还会让用户误以为可以直接去取。

```
生成：在 [100000, 999999] 随机取，撞 uk_o_pickup_code 则重试，最多 10 次
     生成前先查当日该档口已用码集合放内存里排除，降低重试率
核销：商家端扫码或手输 →
      UPDATE o_order SET status='COMPLETED', taken_at=NOW(3)
       WHERE pickup_code=? AND merchant_id=? AND biz_date=CURDATE() AND status='READY'
      影响行数 0 → 提示「码无效或订单状态不符」，不透露具体原因
```

限定 `biz_date` 与 `merchant_id` 是为了防跨天撞码，也避免把别家档口的订单核销掉。

自动完成兜底：出餐后 60 分钟没人取，定时任务从 `READY` 推到 `COMPLETED`。这个时间走 `sys_config.ORDER_AUTO_COMPLETE_MINUTES`。不这么做的话，学生忘了取餐、档口不会每天去打码核销积压订单，商家报表会永久挂着几十个未完成单，营业额就对不上。

## 7 午高峰

真正会打挂系统的是 11:30 到 12:10 的读流量，不是写流量。

`GET /api/merchants/:id/menu` 结果进 Redis，TTL 30 秒，key 含 `stockVersion`。商家改价、下架、调库存时主动删 key。30 秒的库存延迟可以接受，因为最终扣减仍在数据库层做严格校验，缓存只影响"看起来还有"到"下单被拒"的反应速度。

档口列表缓存 60 秒。菜品图片走对象存储加 CDN，绝不让图片流量经过应用进程。

限流分三层：网关按 IP，应用按用户，下单接口按用户加档口。`POST /api/orders` 单用户 3 秒 1 次，超了返回 429。这一层防的是前端按钮被连点，也防脚本刷单。

连接池按 2 核机器配，`connection_limit` 不超过 50。默认值在大内存机器上调小了会明显感觉排队，调大了会把 MySQL 拖垮，两者都要监控等待时长。

## 8 金额一致性

三处必须恒等，任何一处对不上就是 bug：

```
明细行：line_amount = unit_price × quantity + pack_fee - discount_amount
订单头：item_amount = Σ(unit_price × quantity)
        pack_fee    = Σ line.pack_fee
        pay_amount  = item_amount + pack_fee + delivery_fee - discount_amount
        恒等于        Σ line_amount + delivery_fee
支付：  SUCCESS 的 p_payment.pay_amount = o_order.pay_amount
退款：  Σ o_refund.refund_amount(status=SUCCEEDED) <= o_order.pay_amount
```

`scripts/check-schema.mjs` 已经把前三条实现对种子数据做检查，首次运行就抓出十四条金额错误和三条规格项张冠李戴。同一套断言应该在后端做成单元测试和每日对账任务，而不只是脚本。

优惠分摊的尾差处理要固定：按比例分摊时，最后一行用「总额减去前面各行之和」倒推，避免浮点或取整累加导致合计对不上。系统里金额全是整数分，取整用向下取整，尾差归入最后一行。

## 9 幂等清单

需要幂等保护的入口，逐个确认：

| 入口 | 幂等键 | 存储位置 |
|---|---|---|
| 下单 | `user_id` + `client_order_no` | `uk_o_client_order` 唯一索引 |
| 发起支付 | `payment_no` 每次新建，但同一订单只允许一个未关闭的 `PENDING` | 应用层查询加 `uk_p_payment_no` |
| 支付回调 | `payment_no` 加 `channel_txn_no`，状态 CAS | `p_payment.status` |
| 退款回调 | `refund_no` 加 `channel_refund_no` | `uk_o_refund_no` |
| 商家接单 | `order_id` 加 `from_status` CAS | `o_order.status` |
| 核销 | `order_id` 加 `status='READY'` CAS | 同上 |
| SSE 重连 | 按 `lastEventId` 补发 | `o_order.updated_at` |

`p_callback_log` 上刻意没有唯一索引。同一笔交易渠道可能通知多次，日志要全留，幂等在 `p_payment` 的状态上判断。
