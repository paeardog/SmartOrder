# 05 前端方案

三个独立的 Vue 3 应用，不共享运行时，只共享类型与工具函数。

## 工程结构

pnpm workspace 单仓多包。

```
apps/
  h5/            学生端移动网页，Vue 3 + Vite + Vant 4 + Pinia，端口 5173
  web/           学生端桌面网页，Vue 3 + Vite + Pinia，自建设计令牌，端口 5174
  console/       商家端与平台端，Vue 3 + Vite，自建组件与 reactive store，端口 5175
packages/
  api-client/    请求封装（http）、接口定义（endpoints）、错误码（errors）、
                 SSE（events）、跨端业务逻辑（shop/）
  shared/        金额（money）、时间与时钟校正（time）、状态字典（dict）、
                 单号与哈希（id）、本地存储（storage）、文本与拼音（text）、公共样式
```

分三个 app 而不是一个 app 加路由前缀的理由是包体积和权限模型完全不同。学生端要求首屏两秒内可交互，不能背上桌面组件库的体积；商家端在桌面浏览器全天挂着，关心的是断线重连和多窗口同步，不关心首屏；学生桌面端是同一个后端契约下的宽屏形态，主要解决食堂取餐高峰时学生在电脑上下单的场景，跟移动端共用业务逻辑但不共用组件。console 没有引 Element Plus 也没有 Pinia：控制台页面形态固定，自建组件（UiModal、OrderCard 等）加一套 `styles/app.css` 比引库更可控，状态用自建 reactive store。

TypeScript 严格模式开启，`noUncheckedIndexedAccess` 打开。金额类型统一 `type Money = number`（分），格式化只在展示层做，任何地方都不出现 `parseFloat`。

三端全部直连真实后端：请求走 `/api/v1`，Vite dev server 把 `/api` 代理到 `127.0.0.1:8080`，运行时基址可被 `VITE_API_BASE` 覆盖。MSW 模拟层已整体删除，禁止再引 mock 依赖、内存假数据或前端种子。契约一旦改动，`packages/api-client` 的类型会报错，改动点立刻暴露，比口头同步可靠。

## 学生端

### 页面

| 路由 | 页面 | 要点 |
|---|---|---|
| `/` | 首页 | 校区切换、营业中档口列表、进行中订单置顶卡片 |
| `/merchant/:id` | 档口菜单 | 左侧分类锚点，右侧菜品，规格弹层，底部购物车条 |
| `/search` | 搜索 | 菜品与档口混排，历史词存本地 |
| `/cart` | 购物车 | 勾选、改数量、显示起送门槛差额 |
| `/checkout` | 结算 | 进入时生成 `clientOrderNo`，调 `preflight` 拿最终价 |
| `/pay/:orderNo` | 收银台 | 渠道选择，`MOCK` 渠道直接确认，轮询支付结果 |
| `/pay-result/:orderNo` | 支付结果 | 成功/失败/放弃/超时四态，放弃态给取消与继续支付两个出口 |
| `/address` | 收货地址 | 服务端地址簿（`u_address`），配送范围与校区不匹配时在结算页提示 |
| `/orders` | 订单列表 | 按状态分栏，下拉刷新加无限滚动 |
| `/order/:orderNo` | 订单详情 | 取餐码大字展示，倒计时，状态时间轴 |
| `/review/:orderNo` | 评价 | 三项评分加标签，已评价时只读回显；商家回复接口预留，当前恒空 |
| `/coupons` | 优惠券 | 可使用/已使用/已过期三栏，券面与使用门槛同屏 |
| `/favorites` | 我的收藏 | 档口与菜品分栏，取消收藏就地生效 |
| `/notices` | 消息通知 | 按场景配图标，点进对应订单，支持全部已读 |
| `/profile` | 我的 | 学籍认证状态、订单分栏入口、券/地址/收藏/消息聚合 |
| `/login` | 登录 | 学号密码与注册两条路，登录后回跳 `next`；短信与 CAS 接口预留未接 UI |

页面之外的三个约定：

**状态到按钮的映射只写一份，放在 `packages/api-client/src/shop/order.ts`。** 列表卡片、详情页底栏、支付结果页都从这里取动作和主色文案。分栏页各写一套 `if (status === ...)` 的结局一定是列表能取消、详情不能取消，或者反过来，而这种不一致只有用户会先发现。自助取消是否开放取决于 `cancelWindowEndsAt`，判断同样收在这里。

**「再来一单」在前端按当前菜单重建购物车。** 后端没有复制订单的接口，历史订单项只有 `optionText` 文本，需要拿它去匹配现在规格组里的选项名：匹配不上且该组必选时退回默认项，仍凑不齐就不加这道菜并在提示里点名「需重选规格」，菜品下架则点名「已下架」。宁可让用户重选，也不能静默按旧规格下一单。

**取消原因必须落库并回显。** 后端 `cancelOrder` 把 `reason` 写进 `cancel_reason` 和状态日志，详情页据此展示具体原因而不是一句「订单已取消」。早期模拟层吞掉过这个字段，教训是：契约里有的字段，链路上任何一层丢了都等于没验过。

### 关键交互

**结算页的 `clientOrderNo` 必须在进入页面时生成一次并存在内存里，不能每次点提交重新生成。** 否则用户网络卡顿连点两次会产生两笔订单，幂等设计形同虚设。提交失败重试复用同一个值，只有明确放弃并重新进入结算页才换新值。桌面端与 H5 均在 setup 时生成一次，失败重试复用；H5 另保留 `submitting` 锁与 500ms 节流防连点。

**订单详情的取餐码页要能离线看。** 学生进食堂经常信号差，用 `localStorage` 缓存当前进行中的订单，页面加载先渲染缓存再请求刷新。取餐码是纯文本，不需要网络也能给店员看。

**倒计时全部用服务端时间基准。** 首次拿到响应时记录 `serverTime` 与本地 `Date.now()` 的偏移量，之后所有倒计时按偏移校正。学生手机时间不准会导致「明明还有 30 秒却显示已过期」这类诡异现象。

**状态推进靠 SSE 加轮询兜底。** 建立 `EventSource` 订阅自己的订单变更，收到事件后重新拉详情而不是信任事件体。断流后先指数退避重连（1 秒起翻倍、封顶 15 秒），重试超限降级为 5 秒轮询（接单台是 3 秒）。不要只做 SSE——代理、企业网关、iOS 后台挂起都会悄悄断流，而且不报错。

### 移动端适配

`vw` 加 `rem` 混用不如直接 `vw` 配 Vant 默认单位简单。真正要处理的是三个具体问题：

顶部安全区用 `env(safe-area-inset-top)`，底部同理，全面屏不留白会显得廉价。

`100vh` 在 iOS Safari 上包含浏览器工具栏高度，会导致底部购物车条被遮住。用 `100dvh` 并在不支持的浏览器上通过 `window.innerHeight` 写入 CSS 变量兜底。

弹出数字键盘时页面被顶起且不再回落，是 iOS 的已知行为。输入框聚焦后监听 `blur` 手动 `window.scrollTo(0, 当前值)`。

图片一律懒加载加固定宽高比占位，菜单页几十张图不做处理会直接把列表滚成白板。

## 学生桌面端

`apps/web` 是学生端的桌面版本，端口 5174，路由表与 H5 一一对应并多一条 `/merchants`（全部商户列表）：`/`、`/merchants`、`/merchant/:id`、`/search`、`/cart`、`/checkout`、`/pay/:orderNo`、`/pay-result/:orderNo`、`/orders`、`/order/:orderNo`、`/review/:orderNo`、`/coupons`、`/favorites`、`/notices`、`/address`、`/profile`、`/login`，功能对齐 H5，交互换成左侧导航加宽屏双栏：菜单页左分类右菜品，结算页左侧下单信息右侧费用明细，订单详情左侧明细右侧进度时间轴。

不引 Vant，也不用 Element Plus，只保留 `apps/web/src/styles/app.css` 一套设计令牌，与 H5 共享 `packages/shared` 的变量与工具。学生端两个入口共用同一份业务逻辑：`format`、`order`、`sku`、`coupon`、`cache`、`business` 放在 `packages/api-client/src/shop/`，H5 `utils/` 里对应的五个文件是一行 re-export，其余（art、banner、fly、longPress 等）是移动端专用交互工具。谁先改逻辑都不会让两端走偏，这也是同一份契约只维护一次的意思。

**桌面端的 SSE 只在订单相关路由开启。** 浏览器对同源 HTTP/1.1 连接上限是 6 个，`EventSource` 常年占一个；开发期整页刷新频繁，懒加载的视图模块请求会被挤掉，表现为点击导航后主区域空白而侧栏还在。按路由开关连接，`pagehide` 时主动关闭，既省连接也不会在离开订单页后继续拉不存在的数据。

**登录走真实的学号密码。** `/auth/password/login` 与 `/auth/register` 与 H5 是同一套接口，双 token 存 `localStorage`。三端均通过 `configureRequest` 接入 401 自动换发，共享请求层合并并发刷新，迟到的旧 token 401 直接用新 token 重放，每个请求最多重放一次。刷新请求不携带 access token、不触发递归刷新；换发失败或重放仍未授权时清凭证跳登录。开发期演示账号 `admin` / `admin` 由 `V3` 迁移写入，上线前删除或改密。

### 接单台

这是整个项目对稳定性要求最高的页面，档口老板一天到晚就盯着它。

**提醒有三重。** 新单到达时：播放提示音（音量可调，浏览器要求用户手势后才能播声，首次进入需要「开启提示音」按钮，这个引导不能省）、`document.title` 前加未处理单数并闪烁、可选调用 `Notification API` 请求系统通知权限。三者任一生效即可，因为浏览器标签页在后台时会被节流。

**断线要显性告知。** SSE 断开时看板顶部出现红色横条写明「连接已断开，正在重试」，同时启动 3 秒轮询。绝不能静默降级——档口以为没有新单，实际是连接断了，等发现时已经积压二十单，这是会直接导致商家弃用的事故。

**多窗口冲突要处理。** 老板手机和店里电脑可能同时开着接单台。同一单在 A 窗口接了，B 窗口的按钮点击会返回并发冲突错误，此时前端应立即重拉该单状态并刷新对应卡片，而不是弹一个「操作失败」了事。

**接单台不用 offset 分页做增量。** 列表在不断有新单插入，用 `page=2&size=20` 会漏单或重复。当前实现靠 `GET /merchant/orders/summary` 的签名（最新单号加各状态计数）比对：签名变了才重拉对应状态列，新单判定用 PAID 计数增量。`afterId` 游标在接口与类型里已预留，尚未启用；启用后服务端返回大于该 id 的记录，配合 SSE 推送的新单 id 做真正的增量拉取。

## 通用

请求层（`packages/api-client/src/http.ts`）统一做四件事：注入 `Authorization`、解析统一响应包并把非零 `code` 转成带错误码与 traceId 的 reject、从 `x-server-time` 响应头喂时钟校正、给下单附加 `X-Client-Order-No`。三端 401 时用 refresh token 换发并重放原请求，并发请求共享同一个刷新 Promise，最多重放一次，见学生桌面端一节。`X-Idempotency-Key` 头的注入逻辑存在但三端均未使用，写操作幂等当前只有下单这一条真需求。

错误提示区分可恢复与不可恢复。网络层错误显示重试按钮，业务错误显示后端 `message` 且不重试。库存不足、已打烊这类要单独给引导动作，而不是笼统一句失败。

埋点未实现，上线放量前只接必要事件：进入菜单、加购、进结算、提交、支付成功、支付放弃。最后一个是运营最关心的漏斗断点，往往能直接指出是价格问题还是运费问题。

无障碍不是可选项。接单台的「接单」按钮要用真实 `<button>`，取餐码用 `aria-label` 读出，看板状态变化用 `aria-live="polite"`。档口店员长时间高强度操作，键盘可达性能显著影响效率。
