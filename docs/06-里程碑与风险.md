# 06 里程碑与风险

目标是真实运营，不是答辩演示。排期按能在一个学期内跑通真实订单来排，每周有可验收的产出。

## 前置事项（第一周就要启动，全部有外部依赖）

这四件事都不受你控制，任何一件卡住都无法上线。代码可以晚上补，审批不能催。

**ICP 备案。** 7 到 20 个工作日。用学校机房主机则主体是学校，需要信息中心走流程，周期更长且不可控。同时确认是否允许对外提供餐饮服务类网站，部分学校对涉及资金收付的系统审核严格。

**统一身份认证对接申请。** 向信息中心申请 CAS 服务的接入登记，需要提交回调域名、用途说明与管理员信息。拿到测试账号是前置条件，属性字段映射要靠真实返回样本调试。谈不下来就退回手机号加验证码方案，`u_sms_code` 已经准备好了。

**短信通道。** 阿里云或腾讯云短信服务，需要签名与模板审核，校园类签名一般要求学校授权文件。没有授权文件时用「个人验证」类签名会被驳回。这是第二条容易被卡的外部链路。

**食品经营许可与校方准入。** 真实运营必须有入驻协议。平台本身不接触食品，但要留存每个档口的《食品经营许可证》——`m_merchant.license_no` 与 `license_url` 两列就是为此准备，缺证档口一律不给通过审核。出了食品安全问题，这两个字段是平台免责的证据链。

## 排期

### 第 1 周　地基

建库、起服务、CI。`auth` 模块跑通 CAS 与短信双登录，签发双 token 并落 `u_auth_token`。`merchant` 与 `menu` 的增删改查，配一个最小的平台后台能录入两个真实档口和它们的菜单。

验收：手机上打开登录页能用学号登进来，后台能看到刚录的菜品。

### 第 2 周　下单主干

学生端首页、菜单页、购物车、结算页。`POST /api/orders` 全链路，含幂等、价格重算、数据库乐观锁扣库存、状态日志。`MOCK` 支付渠道走完整「预支付、回调、置为已支付」流程。

验收：真机走完一遍下单到支付成功，中间断网点重试不产生重复订单。这一步必须真机测，浏览器模拟器测不出 `100dvh` 和键盘遮挡问题。

### 第 3 周　商家侧闭环

接单台看板、`transit` 状态机、接单出餐核销、取餐码分配与扫码核销、SSE 推流与声音提醒。

验收：两个终端同时操作，出餐后学生端三秒内看到取餐码。**并发冲突测试**：两个浏览器窗口同时点接单，必须恰好一个成功且失败方自动刷新状态。

### 第 4 周　时间相关逻辑

延迟队列、支付超时关闭、超时未取自动完成、兜底扫描、营业时段与临时歇业判定、每日库存初始化。

验收：把 `ORDER_PAY_TIMEOUT_SECONDS` 调成 20 秒，下单不付，观察自动关闭并释放库存；在关闭瞬间完成支付，确认触发自动退款而不是变成已支付。第 6 条竞态分支是这一周的重点，也是最容易被跳过的测试。

### 第 5 周　钱的后路

退款申请、审核、渠道退款、部分退款、退款回调幂等。日汇总任务与商家报表。对账任务。

验收：完整走一遍「支付、申请退款、审核通过、金额回退、报表净额扣减」，各层金额恒等式全部成立。跑 `scripts/check-schema.mjs` 里的金额断言作为单元测试基线。

### 第 6 周　内测放量

三个真实档口入驻，一个食堂门口贴码，限量五十单每天。目标不是订单量，是把真实世界的脏数据引进来：档口手写错价格、学生下单后打电话要求改备注、饭卖完了店员直接在系统外解决。

这一周不写新功能。所有精力放在根据真实反馈调整文案、流程和字段。

### 第 7 周起　正式上线与扩展

去掉限量，接支付真渠道（拿到商户号之后），按 `d_rider` 与 `d_delivery` 开配送。

## 风险清单

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| 学校不批备案或域名 | 中 | 致命，无法公网访问 | 优先争取校内主机（免公网备案），备选云主机加自有主体备案，第二周就要有结论 |
| CAS 不给接入 | 中 | 登录体验降级 | 退回手机号加验证码加学号人工审核，`u_verify_apply` 已备好审核流 |
| 拿不到支付商户号 | 高 | 无法在线收款 | `MOCK` 渠道跑通全流程，收款改为线下扫码加档口手工确认；或接入学校一卡通网关；`channel` 字段可扩展 |
| 短信被刷 | 高 | 直接经济损失 | 图形验证码前置、双维度限流、日上限熔断、异常号码进黑名单 |
| 超卖导致现场纠纷 | 中 | 高，一次就足以让档口退出 | 数据库乐观锁是最终防线不删；Redis 预扣只做流量拦截；拒单流程顺畅，一键拒单自动全额退款 |
| 午高峰宕机 | 中 | 高，错过饭点等于失去用户 | 菜单缓存、静态资源 CDN、连接池监控、`/api/merchants` 降级返回旧缓存 |
| 档口不按系统操作 | 高 | 数据失真，报表不可信 | 出餐动作做到一次点击即可完成；取餐码核销由店员扫码，倒逼线上化；报表差异进运营例会 |
| 学生恶意下单后取消 | 中 | 占用库存与出餐 | `credit_score` 已预留，单日取消超阈值临时限单；未支付订单靠超时自动释放库存 |
| 食品安全事故归责平台 | 低 | 极高 | 留证照、留入驻协议、留订单与出餐时间链，法务文本上线前过一遍学校审核 |
| 团队课业冲突停摆 | 高 | 项目烂尾 | 每周五留可运行状态；文档与 seed 数据保持完整，新人一周内能接手 |

## 该看的三个数

判断这个系统是不是真的在被使用，不看注册数。

**支付完成率**：进入结算页到支付成功的转化。低于七成说明是价格展示或支付方式出了问题。

**出餐实际耗时对比 `avg_prepare_minutes`**：偏差不大说明预估可信，学生按点来取不排队；偏差大就调模型，这是体验的核心变量。

**同一档口一周内复购率**：只有这个指标能证明系统真的解决了排队问题。低于两成说明引流有效但体验没跟上，通常是出餐慢或者状态更新不及时，回去看第二个数。
