# 06 里程碑与风险

目标是真实运营，不是答辩演示。排期按能在一个学期内跑通真实订单来排，每周有可验收的产出。

## 前置事项（第一周就要启动，全部有外部依赖）

这四件事都不受你控制，任何一件卡住都无法上线。代码可以晚上补，审批不能催。

**ICP 备案。** 7 到 20 个工作日。用学校机房主机则主体是学校，需要信息中心走流程，周期更长且不可控。同时确认是否允许对外提供餐饮服务类网站，部分学校对涉及资金收付的系统审核严格。

**统一身份认证对接申请。** 向信息中心申请 CAS 服务的接入登记，需要提交回调域名、用途说明与管理员信息。拿到测试账号是前置条件，属性字段映射要靠真实返回样本调试。谈不下来就退回手机号加验证码方案，`u_sms_code` 已经准备好了。

**短信通道。** 阿里云或腾讯云短信服务，需要签名与模板审核，校园类签名一般要求学校授权文件。没有授权文件时用「个人验证」类签名会被驳回。这是第二条容易被卡的外部链路。

**食品经营许可与校方准入。** 真实运营必须有入驻协议。平台本身不接触食品，但要留存每个档口的《食品经营许可证》——`m_merchant.license_no` 与 `license_url` 两列就是为此准备，缺证档口一律不给通过审核。出了食品安全问题，这两个字段是平台免责的证据链。

## 排期与当前进度

原排期按一个学期跑通真实订单来排。地基到商家闭环已经落地，下面的周次保留为验收口径，状态按当前实现标注。

### 第 1 周　地基　已完成

建库、Flyway 迁移、起服务。学号密码登录与注册跑通，双 token 签发、refresh 落 `u_auth_token` 轮换。档口与菜单增删改查齐全，平台端能审核档口、改全局配置。CAS 与真实短信未接（见「未开始」）。

验收口径：手机上打开登录页能用学号登进来，控制台能看到刚录的菜品。

### 第 2 周　下单主干　已完成

学生端首页、菜单页、购物车、结算页。`POST /api/v1/orders` 全链路，含幂等回放、价格重算、数据库乐观锁扣库存、状态日志、用券与还券。`MOCK` 支付渠道走完整「发起、确认、置为已支付」流程。

验收口径：真机走完一遍下单到支付成功，中间断网点重试不产生重复订单。这一步必须真机测，浏览器模拟器测不出 `100dvh` 和键盘遮挡问题。H5 与 web 均在进入结算页时生成 `clientOrderNo`，失败重试复用同一值；自动测试覆盖重试与重新进入页面两种生命周期。

### 第 3 周　商家侧闭环　已完成

接单台看板、状态机 CAS、接单出餐核销、四位顺序取餐码、SSE 推流与声音提醒、多窗口并发冲突处理。商家端菜品 / 备货 / 营业设置 / 报表 / 档口信息七页齐全，平台端总览 / 审核 / 配置三页齐全。

验收口径：两个终端同时操作，出餐后学生端三秒内看到取餐码。**并发冲突测试**：两个浏览器窗口同时点接单，必须恰好一个成功且失败方自动刷新状态。

### 第 4 周　时间相关逻辑　已完成（扫表方案）

支付超时关闭、超时未取自动完成，都是每 60 秒的幂等扫表，没有延迟队列——当前量级下这就是主路径而不是兜底，Redis 延迟队列是二期优化（`docs/04` 第 4 节）。营业时段与临时歇业判定、库存守卫释放已实现。每日库存初始化任务未实现，备货行由商家端备货页写入。

验收口径：把 `ORDER_PAY_TIMEOUT_SECONDS` 调成 20 秒，下单不付，观察自动关闭并释放库存与券；在关闭瞬间完成支付，确认支付被拒绝而不是变成已支付。MOCK 没有真实资金，「关闭后收款自动退款」分支要等真实渠道接入后补测。

### 第 5 周　钱的后路　部分完成

已有：支付后自助取消窗口内即时退款（直接写 `SUCCEEDED` 退款单）、商家负责人审核本店待退款申请（MOCK 整单退款或驳回恢复原状态）、取消与关单还券释放库存、商家与平台报表从订单表现算。审核具备归属校验、事务锁、重复结论回放及金额上限校验。

未有：学生退款申请接口、拒单自动建退款单、真实渠道退款、部分退款、退款回调幂等、日汇总回写、对账任务。

验收口径：完整走一遍「支付、申请退款、审核通过、金额回退、报表净额扣减」，各层金额恒等式全部成立。`pnpm run check` 的金额断言是静态基线，后端要有对应的单元测试。

### 第 6 周　内测放量　未开始

三个真实档口入驻，一个食堂门口贴码，限量五十单每天。目标不是订单量，是把真实世界的脏数据引进来：档口手写错价格、学生下单后打电话要求改备注、饭卖完了店员直接在系统外解决。

这一周不写新功能。所有精力放在根据真实反馈调整文案、流程和字段。放量前的硬前置见下面「未开始」清单与上线检查表。

## 风险清单

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| 学校不批备案或域名 | 中 | 致命，无法公网访问 | 优先争取校内主机（免公网备案），备选云主机加自有主体备案，第二周就要有结论 |
| CAS 不给接入 | 中 | 登录体验降级 | 退回手机号加验证码加学号人工审核，`u_verify_apply` 已备好审核流 |
| 拿不到支付商户号 | 高 | 无法在线收款 | `MOCK` 渠道跑通全流程，收款改为线下扫码加档口手工确认；或接入学校一卡通网关；`channel` 字段可扩展 |
| 短信被刷 | 高 | 直接经济损失 | 图形验证码前置、双维度限流、日上限熔断、异常号码进黑名单 |
| 超卖导致现场纠纷 | 中 | 高，一次就足以让档口退出 | 数据库乐观锁是最终防线不删；Redis 预扣只做流量拦截；拒单流程顺畅，一键拒单自动全额退款 |
| 午高峰宕机 | 中 | 高，错过饭点等于失去用户 | 当前直查库，放量前压测；菜单缓存、静态资源 CDN、连接池监控、档口列表降级返回旧缓存都是待上线的优化项 |
| 档口不按系统操作 | 高 | 数据失真，报表不可信 | 出餐动作做到一次点击即可完成；取餐码核销由店员扫码，倒逼线上化；报表差异进运营例会 |
| 学生恶意下单后取消 | 中 | 占用库存与出餐 | `credit_score` 已预留，单日取消超阈值临时限单；未支付订单靠超时自动释放库存 |
| 食品安全事故归责平台 | 低 | 极高 | 留证照、留入驻协议、留订单与出餐时间链，法务文本上线前过一遍学校审核 |
| 团队课业冲突停摆 | 高 | 项目烂尾 | 每周五留可运行状态；文档与 seed 数据保持完整，新人一周内能接手 |

## 该看的三个数

判断这个系统是不是真的在被使用，不看注册数。

**支付完成率**：进入结算页到支付成功的转化。低于七成说明是价格展示或支付方式出了问题。

**出餐实际耗时对比 `avg_prepare_minutes`**：偏差不大说明预估可信，学生按点来取不排队；偏差大就调模型，这是体验的核心变量。

**同一档口一周内复购率**：只有这个指标能证明系统真的解决了排队问题。低于两成说明引流有效但体验没跟上，通常是出餐慢或者状态更新不及时，回去看第二个数。
