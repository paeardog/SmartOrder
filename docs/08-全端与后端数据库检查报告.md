## 1. 结论

商家端、学生 Web、学生 H5、H5 内的骑手工作台，以及后端和数据库均已有实际实现，并非只有页面或接口占位。当前代码能够通过类型检查、生产构建和现有单元测试，但仍存在权限绕过、跨店数据破坏、价格校验缺失、库存与交易一致性、前端会话隔离和配送异常处置等问题，不宜直接作为生产可用版本。

## 4. 安全与数据隔离

### S01 · P0 · 短信登录没有验证手机号持有权

**确认方式：静态确认。**

- `sendSmsCode` 写入固定验证码，随后短信登录直接按手机号查找用户并创建会话；没有真实短信发送，也没有按运行环境关闭该占位逻辑。接口在鉴权白名单内，不能仅因前端未展示入口而认为不可达。
- 前提是相关接口对外可达、目标用户绑定手机号且状态可用；请求者无需实际收到短信即可登录。发送频率、失败计数和验证码原子消费也没有形成完整约束。
- 建议：未接入真实短信前关闭该登录通道；接入后使用随机验证码、发送限流、失败次数限制和原子消费。不要只在页面隐藏入口。
- 证据：[AuthService.java:48-98](../server/src/main/java/com/campus/smartorder/auth/service/AuthService.java#L48)、[JwtAuthenticationFilter.java:27-41](../server/src/main/java/com/campus/smartorder/auth/service/JwtAuthenticationFilter.java#L27)。

### S02 · P0 · 新增或编辑无规格菜品可能删除全站既有规格项

**确认方式：静态确认；未执行破坏性复现。**

- `saveGroups` 在当前菜品没有旧规格组时，通过 `.in(!existing.isEmpty(), ...)` 省略查询条件，导致 `existingOptions` 读取全表；随后将不在本次保留集合中的选项按 ID 批量删除。
- 正常新增菜品提交 `groups: []` 就满足条件，影响范围可能跨菜品、跨商家。即便配置了全表删除拦截器，这里删除语句仍带 ID 条件，不能依赖它识别错误的业务范围。
- 当前库已有 14 个空规格组、10 个必选空规格组，商家页面也能观察到零选项分组；**这只证明当前数据异常，不证明历史成因就是此缺陷**。
- 建议：旧组集合为空时，旧选项直接取空集合；查询与删除始终限定本菜品所属组；在隔离库补“新建无规格菜品不改变其他商家选项”的回归，再核查历史规格数据。
- 证据：[MerchantMenuService.java:543-556](../server/src/main/java/com/campus/smartorder/merchant/service/MerchantMenuService.java#L543)、[MerchantMenuService.java:630-635](../server/src/main/java/com/campus/smartorder/merchant/service/MerchantMenuService.java#L630)、[MenuView.vue:343-363](../apps/console/src/views/MenuView.vue#L343)。

### S03 · P1 · 平台路径鉴权可被等价路径写法绕过

**确认方式：运行复现，仅使用 GET。**

- 鉴权用原始 `getRequestURI()` 的字符串前缀判断，MVC 使用解析后的路径。两者对编码字符和分号路径参数的解释不同。
- 同一普通学生令牌访问 `/api/v1/platform/overview` 得到 HTTP 403 / `code=20003`；访问编码路径 `/api/v1/pl%61tform/overview` 或分号路径 `/api/v1/platform;x/overview` 得到 HTTP 200 / `code=0`，返回平台统计字段。
- 平台控制器部分写操作同样没有方法级二次鉴权，存在同类风险；本次未调用写接口，不将写越权表述为已动态复现。
- 建议：授权依据与实际匹配 Handler 使用一致路径语义，敏感操作增加统一的主体/角色校验；补普通学生、店员及编码/分号路径的集成测试，不能仅依赖代理层过滤。
- 证据：[JwtAuthenticationFilter.java:54-95](../server/src/main/java/com/campus/smartorder/auth/service/JwtAuthenticationFilter.java#L54)、[ConsoleAccess.java:19-49](../server/src/main/java/com/campus/smartorder/console/ConsoleAccess.java#L19)、[PlatformController.java:27-51](../server/src/main/java/com/campus/smartorder/console/PlatformController.java#L27)。

### S04 · P1 · 下单规格差价可由客户端影响

**确认方式：静态确认。**

- `hydrate` 遇到不存在或为空的规格 ID 时保留原始输入，`unitPrice` 随后直接累加其差价；直接下单的解析路径没有调用购物车新增时的完整规格校验。
- 可造成负差价压低订单金额；未知规格、跨菜品规格、重复选项或漏选必选组也缺少统一拒绝机制。
- 建议：价格完全从数据库生成；未知规格立即拒绝，统一校验归属、状态、去重、必选及数量规则，并让购物车和下单共用校验。
- 证据：[PricingService.java:57-94](../server/src/main/java/com/campus/smartorder/merchant/service/PricingService.java#L57)、[CartService.java:170-183](../server/src/main/java/com/campus/smartorder/cart/service/CartService.java#L170)、[OrderService.java:399-427](../server/src/main/java/com/campus/smartorder/order/service/OrderService.java#L399)。

### S05 · P1 · 订单商家与菜品商家没有一致性校验

**确认方式：静态确认。**

- 下单按请求商家生成订单归属、取餐点和优惠券范围，却按提交的菜品 ID 计价、扣库，没有要求菜品属于该商家。
- 传商家 A 与菜品 B，可形成归属 A、消耗 B 库存的订单；未指定购物车行时，解析还可能包含该用户多个商家的选中行。
- 建议：后端从菜品确定并核对商家归属，拒绝跨店混单；购物车解析显式限定订单商家，不信任客户端 merchantId。
- 证据：[OrderService.java:381-435](../server/src/main/java/com/campus/smartorder/order/service/OrderService.java#L381)、[CartService.java:170-194](../server/src/main/java/com/campus/smartorder/cart/service/CartService.java#L170)。

### S06 · P1 · 正式提交没有复用营业和可售校验

**确认方式：静态确认。**

- 预检检查营业时段、临时休息；创建订单只检查商家业务状态，没有重新调用营业状态计算。客户端可跳过预检，或在预检后状态变化时提交。
- 菜品解析只明确拒绝下架状态，没有统一拒绝软删除、手动售罄和供应时段外的菜品。
- 建议：预检与创建共用服务端可售规则，正式提交必须重新校验；保留事务内原子库存占用，不能让预检成为唯一校验点。
- 证据：[OrderService.java:123-135](../server/src/main/java/com/campus/smartorder/order/service/OrderService.java#L123)、[OrderService.java:160-175](../server/src/main/java/com/campus/smartorder/order/service/OrderService.java#L160)、[OrderService.java:399-425](../server/src/main/java/com/campus/smartorder/order/service/OrderService.java#L399)。

### S07 · P1 · 后台账号停用或降权后，旧访问令牌保留原权限

**确认方式：静态确认；未修改账号状态验证。**

- ACCOUNT 请求分支直接使用 JWT 中的角色、商家归属，没有核对数据库中的当前账号状态或权限版本；学生主体已有状态检查，二者不一致。
- 已登录后台账号被停用、降权或换绑后，旧 access token 在到期前仍可能按旧权限访问；商家 SSE 授权也需要同步处理撤权。
- 建议：统一校验账号可用状态与权限版本，撤权时使旧凭证和相关订阅失效。
- 证据：[JwtAuthenticationFilter.java:77-95](../server/src/main/java/com/campus/smartorder/auth/service/JwtAuthenticationFilter.java#L77)、[EventStreamController.java:51-55](../server/src/main/java/com/campus/smartorder/events/api/EventStreamController.java#L51)。

### S08 · P1 · 后台刷新令牌无法真正轮换与注销

**确认方式：静态确认。**

- 后台 refresh 仅验签并查询账号状态，不记录该刷新会话、已使用令牌或撤销状态；logout 只删除学生刷新令牌表中的记录。
- 保留的后台 refresh token 在退出后仍可换发，旧令牌在“刷新”后也可继续使用；改密是否要求撤销其他会话也没有统一实现。
- 建议：为 ACCOUNT 建立独立会话存储，原子轮换刷新令牌并支持退出、改密、停用撤销，不要写入只关联学生的令牌外键表。
- 证据：[ConsoleAccountService.java:66-95](../server/src/main/java/com/campus/smartorder/console/ConsoleAccountService.java#L66)、[AuthService.java:241-243](../server/src/main/java/com/campus/smartorder/auth/service/AuthService.java#L241)。

### S09 · P1 · 迟到的 401 或刷新结果会越过账号切换边界

**确认方式：静态确认，并由隔离测试桩复现。**

- 请求层发现当前 token 与原 token 不同时，直接用当前 token 重放原请求，没有区分“同账号续期”和“换成另一个账号”。旧刷新返回 false 后，又会触发全局 `onUnauthorized` 清会话。
- 测试桩观察到同一接单 POST 先带会话 A、随后带会话 B；另一用例观察到旧刷新结束后清除了 B。仅使用内存假响应，没有向真实后端接单。
- H5 中 `refreshSession` 防止覆盖新凭证的检查只解决了局部问题，上层重放和清会话仍不安全；共享请求层也被 Web/控制台使用。
- 建议：请求、刷新和未授权回调绑定会话代次；跨会话不重放、不清理、不写回旧结果，并增加完整请求层到 bootstrap 的测试。
- 证据：[http.ts:150-167](../packages/api-client/src/http.ts#L150)、[H5 session.ts:67-79](../apps/h5/src/stores/session.ts#L67)、[H5 bootstrap.ts:20-24](../apps/h5/src/bootstrap.ts#L20)。

## 5. 商家端、Web 与 H5 交互问题

### F01 · P1 · H5 私人订单缓存未按账号隔离

**确认方式：静态确认。**

- 订单列表缓存键只有状态、页码，详情键只有订单号；缓存落在 localStorage，退出只清 token/profile，不清订单缓存。
- 同浏览器 A 换成 B 后，可能先显示 A 的旧订单，接口失败时还会保留。`cachePeek` 本身也不检查 TTL，不能指望过期自动消除暴露。
- 建议：私人缓存按用户标识隔离，退出清理相关 store、缓存及保活页面，并使旧会话请求失效。这是客户端数据暴露，不等同于后端订单接口越权。
- 证据：[OrdersView.vue:172-174](../apps/h5/src/views/OrdersView.vue#L172)、[OrdersView.vue:308-324](../apps/h5/src/views/OrdersView.vue#L308)、[OrderDetailView.vue:439-445](../apps/h5/src/views/OrderDetailView.vue#L439)、[cache.ts:9-34](../packages/api-client/src/shop/cache.ts#L9)、[session.ts:57-65](../apps/h5/src/stores/session.ts#L57)。

### F02 · P1 · 部分勾选结算后，未勾选商品也被清空

**确认方式：静态确认；未提交真实订单。**

- Web/H5 创建订单只提交选中行，成功后却调用整档口 `cart.clear`。同店 A、B 两项只买 A，B 仍会被删除；H5 还清理了整个目标分组的菜品备注。
- 后端已经只删除本次使用的购物车行，前端的额外整店删除没有必要。
- 建议：创建成功后刷新购物车，只清理实际提交项对应的本地备注。
- 证据：[Web CheckoutView.vue:209-228](../apps/web/src/views/CheckoutView.vue#L209)、[H5 CheckoutView.vue:599-637](../apps/h5/src/views/CheckoutView.vue#L599)、[CartService.java:154-161](../server/src/main/java/com/campus/smartorder/cart/service/CartService.java#L154)、[OrderService.java:237-245](../server/src/main/java/com/campus/smartorder/order/service/OrderService.java#L237)。

### F03 · P1 · 商家看板部分列加载失败后可能长期不再补拉

**确认方式：条件风险，错误处理与签名提交顺序已确认。**

- 状态列加载吞掉异常；外层仍提交汇总签名并将失败数清零。之后若汇总数量和最新订单号不变，`sync` 就跳过列加载。
- 可出现数量正确、某列为空或数据陈旧的情况，后续正常请求也不一定恢复，影响接单处理。

### B01 · P1 · 优惠券核销竞争失败不会回滚折扣订单

### B02 · P1 · 模拟支付确认与取消竞争会形成不一致账态

- 生产首次执行相应迁移时，可能创建已知口令身份或覆盖已有学生密码。这里的学生演示账号不是平台管理员，但仍可获得学生业务能力。
- 建议：演示数据与正式迁移隔离；对已执行环境核查、停用或改密，不修改已发布迁移来规避校验，也不要仅隐藏登录提示。
- 证据：[V2:24-33](../server/src/main/resources/db/migration/V2__student_password_and_marketing.sql#L24)、[V3:4-12](../server/src/main/resources/db/migration/V3__student_demo_admin_account.sql#L4)、[application.yml:31-37](../server/src/main/resources/application.yml#L31)。

### D02 · P1 · 持续重写 V1 与存量库升级机制冲突

**确认方式：条件风险；当前实例未发现迁移失败。**

- 生成器固定覆盖 V1，检查器要求 V1 与当前 schema 相等；数据库却会保存已执行 V1 的校验和，且启动启用了迁移校验。
- 一旦已部署数据库执行过旧 V1，之后修改并重新生成 V1，可能在启动校验时失败，新增后续迁移不能自动消除此冲突。
- 建议：冻结已发布迁移，先更新 schema 真源，再新增增量迁移；将一致性检查升级为“冻结迁移链重放后的最终结构与 schema 等价”。分别测试空库初始化和旧版本升级，不能通过禁用校验或随意 repair 处理。
- 证据：[gen-flyway.mjs:31-61](../scripts/gen-flyway.mjs#L31)、[application.yml:31-37](../server/src/main/resources/application.yml#L31)。

### D03 · P1 · 测试库防误删遗漏自定义库名的大小写别名

**确认方式：静态确认；本机大小写不敏感条件已只读确认。**

- runner 用大小写敏感比较判断测试库是否等于业务库，之后执行 DROP DATABASE；只对固定名称 smartorder 额外做了小写判断。
- 当自定义业务库名与测试库名只差大小写时，可能指向同一数据库并通过检查。本机 `lower_case_table_names=1`，确实存在大小写别名语义；默认 smartorder 名称有额外保护，不是默认运行必然误删。
- 建议：规范化后比较，强制独立测试库命名规则，并使用无业务库删除权限的专用账号；不在现有业务库试验此场景。
- 证据：[run-db-tests.mjs:89-125](../scripts/run-db-tests.mjs#L89)。

### D04 · P2 · 单独重跑 seed 时没有清理完整关联集合

**确认方式：静态确认；当前库未发现所抽查的孤儿记录。**

- seed 关闭外键检查后清空用户等表，却遗漏地址、用户券、券模板；这是单独重跑 seed 的问题，不是新建空库必然发生的问题。
- 残留记录可能成为孤儿，或错误关联到复用的用户 ID；恢复外键检查不会自动追溯验证既有数据。
- 建议：明确完整的开发数据重置集合及使用边界，补重复初始化后的引用检查；任何真实数据环境都不能直接执行重置脚本。
- 证据：[seed.sql:4-36](../db/seed.sql#L4)。

### D05 · P2 · 数据库行为测试对结果值缺少断言

**确认方式：静态确认；本次未运行重建库测试。**

- runner 主要比较进程退出码/错误号；CAS 的 ROW_COUNT、查询结果和 EXPLAIN 仅打印，没有匹配预期值和执行计划。
- SQL 正常执行但 CAS 全部零行、目标数据不存在或查询计划退化时，相关测试仍可能通过。“19 项通过”不能证明所有这些行为符合预期。
- 建议：为行数、状态、金额和计划建立机器断言，增加空库迁移、旧库升级、重复 seed 和并发库存/优惠券测试。
- 证据：[run-db-tests.mjs:160-176](../scripts/run-db-tests.mjs#L160)、[06-status-cas-rowcount.sql:1-7](../db/tests/06-status-cas-rowcount.sql#L1)、[18-index-usage.sql:1-5](../db/tests/18-index-usage.sql#L1)。

## 9. 能力边界与尚未验证的部分

1. **真实支付仍未接入。** 当前默认通道为 MOCK；模拟确认、模拟退款成功不等于银行/第三方资金结算。真实渠道签名回调、补偿、对账、退款到账等必须另行验收。现有文档已明确学生主动申请退款、拒单自动退款等能力边界，不将“有退款审核”误写成“退款业务全部闭环”。参见 [接口契约:176-178](03-后端规划与接口契约.md#L176)。
2. **开发配置不能直接上线。** 默认 profile 为 dev，仍需显式生产配置、独立签名密钥和数据库凭据、清理演示账号、核查端口暴露与 HTTPS。本次没有证明真实生产密钥泄漏，也没有扫描公网。证据：[application.yml:13-14](../server/src/main/resources/application.yml#L13)。
3. **数据库静态通过不等于当前数据完整。** 当前必选空规格组是实际数据问题；五类一致性抽查为零只是有限观察，不覆盖全部外键、历史快照、金额、配送孤儿或业务状态组合。
4. **并发和故障场景尚需隔离环境。** 包括支付与取消竞争、同券双订单、补货与下单、事务回滚后的通知、配送中停用/转派、长时间网络悬挂、服务重启和多实例推送。
5. **视觉、性能和部署不在已完成验收范围。** 没有做移动端全机型、浏览器兼容、可访问性、压力测试、备份恢复演练、依赖漏洞全量扫描或生产网关验证。

## 10. 建议修复顺序与验收重点

### 第一批：阻断权限与数据破坏

- S01：未完成短信接入前关闭通道；有效随机验证码以外的登录应全部失败。
- S02：隔离库新增/编辑无规格菜品后，其他菜品及其他商家的规格数量、内容完全不变；对现有空必选组单独核查修复来源。
- S03：普通学生和店员对正常、编码、分号等价路径均按同一权限拒绝，覆盖平台读写 Handler。
- S04/S05/S06：未知/跨店规格、客户端差价、跨店购物车、打烊/售罄/删除菜品等输入应被服务端拒绝，且不产生订单、不占库。

### 第二批：交易一致性与换号隔离

- B01—B05：同券最多一个订单享受优惠；取消与支付只能形成允许的终态组合；补货不能覆盖锁定/销量；切库存模式不影响旧订单占用；规格库存扣减与归还守恒。
- S07—S09、F01：停用、降权和退出后权限按约定失效；旧账号请求不能以新账号重放；新账号不出现旧账号订单缓存。
- F02：部分选中下单后，未选商品及对应备注保持不变。

### 第三批：履约与页面正确性

- R01/R02：配送异常有受控收尾，学生和骑手看到相同的下单地址快照。
- F03/F05、B07/B08：单列失败、提交前后、超过扫描批次及断线恢复后，最终页面与数据库状态一致。
- F04、F06—F11、R03/R04：备注可达、旧订单可查询、规格替换正确、编辑不清无关字段、地址失败不报成功、离页停止轮询、未登录可按设计浏览、退出不被网络悬挂锁住。

### 第四批：可重复升级与上线验收

- D01—D05：正式迁移不生成演示身份；旧库升级无需篡改已执行迁移；测试账号无权删除业务库；数据初始化与行为断言可重复验证。
- 在独立 MySQL、独立后端端口和隔离账号下补齐真实链路测试，再评估生产发布；不要在现有业务库上以删表、重置或制造竞争的方式验证本报告。
