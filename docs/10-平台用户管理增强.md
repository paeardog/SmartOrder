# 平台用户管理增强 — 功能说明

> 日期：2026-11-19
> 规格与任务：[spec.md](../.trae/specs/platform-user-admin/spec.md) / [tasks.md](../.trae/specs/platform-user-admin/tasks.md)
> 涉及端：后端 `server/`、平台控制台 `apps/console/`、学生端 `apps/h5/`

---

## 1. 背景

此前控制台「用户管理」只有列表、详情、封禁/解禁三类能力：

- 新用户通过学号密码注册后 `verify_status` 固定为 1（待审核），但平台没有通过/驳回按钮；
- 注册流程不采集手机号、学院、校区，平台也没有资料修改入口；
- 没有删除用户能力。

结果是待审核用户长期滞留，且资料长期不完整。本次补齐平台侧的用户审核、资料编辑与删除能力。

---

## 2. 能力总览

| 能力 | 入口 | 说明 |
|---|---|---|
| 认证审核 | 用户列表行操作 / 详情 | 通过（`1/0/3 → 2`）、驳回（`1 → 3`，原因必填）；被驳回可「重新通过」 |
| 编辑资料 | 用户列表行操作 / 详情 | 昵称、真实姓名、学号、手机号、学院、校区、宿舍楼 |
| 删除用户 | 用户列表行操作 / 详情 | 有订单记录时拒绝并提示改用封禁；无订单时物理删除 |
| 驳回原因展示 | 学生端个人页 | 认证状态为「认证驳回」时显示平台填写的原因 |

`verify_status` 取值：`0 未提交` / `1 待审核` / `2 通过` / `3 驳回`。

---

## 3. 后端接口

均位于 `/api/v1/platform/users`，仅 `PLATFORM_ADMIN` 可调用（沿用 `ConsoleAccess.enforce`）。

### 3.1 认证审核

`PATCH /api/v1/platform/users/{userId}/verify`

```json
{
  "verifyStatus": 2,
  "expectedVerifyStatus": 1,
  "reason": "资料完整"
}
```

- `verifyStatus` 只接受 `2`（通过）或 `3`（驳回）；
- 驳回时 `reason` 必填，长度 ≤ 255 字；
- 通过允许当前状态 `0/1/3`；驳回仅允许当前状态 `1`；
- 使用 `expectedVerifyStatus` 做 CAS，状态已被其他管理员修改时返回「认证状态已变更，请刷新后重试」。

响应为更新后的用户行。

### 3.2 编辑资料

`PATCH /api/v1/platform/users/{userId}/profile`

```json
{
  "nickname": "小林",
  "realName": "林同学",
  "studentNo": "202611180001",
  "phone": "13800000000",
  "college": "计算机学院",
  "campusArea": "中心校区",
  "dormBuilding": "紫荆公寓 1 栋"
}
```

- 字段均可选，未传字段保持不变；传空串表示清空（手机号/学号写 `NULL`）；
- 手机号：空 或 11 位大陆手机号（`^1[3-9]\d{9}$`），全局唯一；
- 学号：空 或 4–32 位字母数字，全局唯一（兼容演示账号 `admin`）；
- 其余字段按数据库列长度校验，提交前 trim；
- 唯一冲突返回明确错误码，不暴露 SQL。

### 3.3 删除用户

`DELETE /api/v1/platform/users/{userId}`

- 若该用户在 `o_order` 中存在订单记录，返回 `60003`，提示「该用户存在订单记录，为保证对账请改用封禁」；
- 否则物理删除，依赖既有外键级联清理：`u_verify_apply`、`u_campus_binding`、`u_auth_token`、`u_favorite`、`u_address`、`u_cart_item`、`mk_user_coupon`、`n_notify_message` 级联删除，`d_rider.user_id` 置空；
- 删除后该用户已签发的 token 在下一次请求时因用户不存在而失效。

### 3.4 新增错误码

| 错误码 | 含义 |
|---|---|
| `60001` | 手机号已被其他用户使用 |
| `60002` | 学号已被其他用户使用 |
| `60003` | 该用户存在订单记录，为保证对账请改用封禁 |

## 4. 数据模型变更

新增 Flyway 迁移 `V5__user_verify_note.sql`：

```sql
ALTER TABLE `u_user`
  ADD COLUMN `verify_note` VARCHAR(255) NOT NULL DEFAULT ''
  COMMENT '认证审核备注/驳回原因' AFTER `forbidden_reason`;
```

- 迁移使用 `information_schema.COLUMNS` 判重，存量库可重复执行；
- 驳回原因只保留最新一条，不做历史记录；
- `AuthService.profile` 同步返回 `verifyNote`，供学生端展示。

## 5. 控制台交互

页面：控制台 → 用户管理（`/platform/users`）。

- 行操作：`详情`、`通过 / 驳回 / 重新通过`、`编辑`、`封禁 / 解禁`、`删除`；
- 审核弹窗：通过可填备注，驳回必须填原因，提交中禁用按钮；
- 编辑弹窗：7 个字段回填，前端先做手机号/学号格式校验，保存成功后局部刷新该行；
- 删除弹窗：明确提示「不可恢复」及被清除的数据范围；后端返回订单守卫错误时，错误展示在弹窗内、不关闭弹窗；
- 详情弹窗：补充宿舍楼与认证备注，底部提供「编辑资料 / 删除用户」。

学生端个人页在认证被驳回且存在原因时，展示「认证驳回：…」提示块。

---

## 6. 权限与并发

- 平台接口仅 `PLATFORM_ADMIN` 可调用；学生 token、商家账号调用返回 `403`。
- 审核与封禁均使用 expected 状态做 CAS，避免多管理员并发覆盖。
- 编辑资料只更新白名单字段；接口不返回 `password_hash`。
- 删除以订单守卫兜底，避免产生订单/退款对账孤儿数据。

## 8. 已知边界

- 本次未做学生端资料自助编辑，平台代改后学生下次登录/刷新 profile 可见新资料；
- 未做批量审核、批量删除；
- 未接入 `u_verify_apply` 的证件照上传与审核流程；
- 删除为不可恢复操作，生产环境建议先备份或限制为管理员在低峰期执行。
