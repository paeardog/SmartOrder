# 01 需求规格说明书

## 1 项目背景与目标

高校食堂的排队瓶颈集中在下课后四十分钟。学生提前在手机上点好，到档口直接取餐，可以把点单和付款的时间从窗口移走。SmartOrder 就是这个场景的预点单系统：主流程是档口预点单加到店自取，配送作为数据模型和接口已预留的扩展形态，由 `d_rider`、`d_delivery` 两张表和配送员接口支撑。

系统要解决的不是演示效果，而是三个具体问题。价格、规格和库存在下单时必须以数据库当前值为准，不能有客户端报价的空间；高峰期多终端同时操作同一单时状态不能错乱；商家要在电脑和手机之外，用一台放在档口的电脑全天挂着接单台，断线后要能立刻知道。

目标用户是一个校区内的学生、入驻档口和平台运营方。系统按单实例部署设计，校园量级下不引入微服务、Redis 或消息队列，先把 MySQL 事务与索引用到位。

## 2 用户与角色

| 角色 | 主体类型 | 入口 | 权限边界 |
|---|---|---|---|
| 学生 | USER | H5 `5173`、Web `5174` | 浏览档口与菜单、下单支付、查看自己的订单、评价、收藏、地址、通知、券 |
| 商家负责人 | ACCOUNT / `MERCHANT_OWNER` | 控制台 `5175` | 本店全部业务，含菜单、营业、备货、报表、退款审核 |
| 商家店员 | ACCOUNT / `MERCHANT_STAFF` | 控制台 `5175` | 本店只读，以及接单、制作、出餐、核销、拒单五个写操作 |
| 平台管理员 | ACCOUNT / `PLATFORM_ADMIN` | 控制台 `5175` | 平台总览、档口审核、全局配置、平台用户管理 |
| 配送员 | USER + 配送资格 | H5 登录页选择配送员登录 | 查看配送任务、抢单、取餐、送达 |

两套账号体系彼此独立。学生用学号登录，控制台账号由 `sys_account` 管理，不能互相混用。学生端展示的 `admin` 只是演示学生，控制台的 `admin` 是平台管理员。

## 3 功能需求

### 3.1 学生端

**登录与身份。** 学号加密码登录与注册是主入口，短信验证码登录链路已实现但开发环境使用固定验证码，CAS 只有路由预留。登录返回 access token 与 refresh token，access token 两小时过期，refresh token 三十天有效且刷新后旧值作废。当前用户信息通过 `/auth/profile` 获取，包含认证状态与信用分。

**浏览与选购。** 首页按校区列出营业中的档口，支持搜索菜品与档口混排。档口菜单接口把分类、菜品、规格组、库存一次返回，避免串行请求。菜品支持规格组与加料组：单选互斥、份量选择、多选加价在同一菜品上共存。库存有当日限量与不限量两种模式，售罄和打烊在菜单上直接体现。服务端购物车按档口分组，同规格的加购累加数量，切换档口时提示清空原购物车。

**结算与下单。** 结算页先调用预校验拿到最终价格与库存状态，提交时强制携带 `X-Client-Order-No` 幂等键。订单金额由服务端从数据库重算，请求体中的任何金额字段都不参与计算。支付渠道当前只有 `MOCK`，支付确认与轮询结果都走真实接口。未支付订单超过时限由定时任务关闭并释放库存与券；已支付后可在一个短窗口内自助取消，窗口外走退款审核。

**订单与取餐。** 订单列表按状态分栏，详情展示状态时间轴、取餐码和倒计时。倒计时以服务端时间基准校正，避免学生手机时钟不准造成误判。状态推进靠 SSE 推送，断线后降级轮询。已出餐订单支持按取餐码核销，超时未取自动完成。已完成订单可以评价，一单一评，支持匿名、三项评分、标签和晒图，商家回复字段已预留但接口未实现。

**个人中心。** 包含优惠券、收藏、收货地址、站内信、我的评价入口。地址簿落在服务端 `u_address`，配送范围与校区不匹配时在结算页提示。收藏区分档口与菜品，取消后即时生效。消息通知按场景跳转对应订单，支持全部已读。

### 3.2 商家控制台

**接单台。** 状态分栏看板是全天常开的界面。新单到达时有提示音、标题闪烁和系统通知三重提醒，浏览器要求首次用户手势后才能播放声音。SSE 断开时顶部显示断连横条并启动三秒轮询，不允许静默降级。同一单被两个窗口同时操作时，冲突方立即重拉状态而不是弹一个笼统的失败提示。列表增量依靠汇总接口的签名比对，不依赖容易漏单的 offset 分页。

**订单处理。** 接单、开始制作、出餐、核销、拒单各对应一条带前态条件的更新语句。出餐时分配取餐码、把库存占用转为已售、写站内信在同一个事务里完成。拒单必须填写原因。历史订单页提供筛选、退款待处理和负责人审核入口，审核只支持 MOCK 整单退款，同意时校验金额上限并释放库存与券，驳回时按状态日志恢复到退款前状态。

**档口经营。** 菜品管理含分类排序、菜品增改、规格配置、批量上下架。备货页按营业日快速调整库存并支持一键售罄。营业设置管理每周时段、临时歇业和当日调整，手动恢复营业会写入当日 `OPEN` 覆盖记录，学生端与控制台共用同一份营业判定。档口信息页维护名称、招牌、证照和联系方式。报表页展示今日实时看板与历史趋势，日序列按日期升序补零返回，前端「对比昨日」依赖这个顺序。

**报表口径。** 流水是已支付且非 `CLOSED` / `CANCELLED` 订单的实付合计，净额是流水减去已退款。报表从 `o_order`、`o_order_item`、`o_refund` 现场聚合，`st_merchant_daily` 与 `st_dish_daily` 只是历史落表，不是读取源。

### 3.3 平台控制台

平台总览给出档口与菜品计数、十四天趋势、今日流水净额和校区列表。档口审核对待审档口执行通过或驳回，驳回需要理由。全局配置页维护运行期配置，例如支付开放渠道、下单最低认证状态、支付超时时长。`sys_config` 的改动即时生效，放量前必须逐项确认取值。平台用户管理已有页面与接口，学籍认证审核流当前只有表没有接口。

### 3.4 配送员

配送员复用学生账号密码，但必须具备已启用的配送资格。H5 登录页选择配送员登录后进入配送工作台：查看本人资料、切换接单状态、查看配送任务、接任务、取餐、送达。配送单状态为 `WAITING`、`ACCEPTED`、`PICKED`、`DELIVERED`、`FAILED`，按目标楼栋分组便于顺路派单。业务主形态仍是到店自取，配送流程不参与当前默认的下单主路径。

### 3.5 系统侧

| 任务 | 频率 | 说明 |
|---|---|---|
| 支付超时关单 | 每 60 秒 | 扫描待支付且已过期的订单，条件更新为 `CLOSED`，释放库存与券 |
| 取餐超时完成 | 每 60 秒 | 扫描已出餐且超过取餐时限的订单，条件更新为 `COMPLETED` |
| SSE 兜底扫描 | 每 3 秒 | 回看订单更新时间，与内存状态比对去重后补推 |
| SSE 心跳 | 每 20 秒 | 向所有订阅连接发送 `ping` |

健康检查 `/system/health` 返回数据库真实状态，包括会话时区、隔离级别、业务表数和 Flyway 版本，用来区分「进程活着」和「库是好的」。

## 4 业务规则

**金额。** 全链路用整数分表示金额，数据库列是 `INT UNSIGNED` 或 `BIGINT UNSIGNED`，不使用浮点和 `DECIMAL`。展示层的格式化是唯一允许出现小数点的位置。评分同理，`rating_score` 在商家表上存百分制，评价表里按 1 至 5 存。

**价格与库存。** 服务端在下单事务内重算全部价格，客户端只提交档口、购物车行、备注、联系人、履约方式、券和幂等键。库存扣减是带余额条件的单行更新，影响行数为 0 即售罄。出餐时 `stock_locked` 转为 `stock_sold`，取消和关单时释放 `locked`。规格项库存为 `NULL` 表示不限量。

**幂等。** 前端进入结算页时生成一次 `clientOrderNo`，提交失败重试复用同一个值。数据库用 `(user_id, client_order_no)` 唯一键兜底，撞键时回查原订单返回成功，不能让用户看到「下单失败」但实际已生成订单。

**状态机。** 状态流转集中在一张转移表里，非法转移直接拒绝。落库全部使用把前态写进 `WHERE` 的条件更新，影响行数 0 视为并发冲突，由业务层复查后返回对应错误码。状态日志与状态变更在同一事务里写入。终态不再接受任何转移。

**权限。** 控制台权限在后端一处收口。`/merchant/*` 要求 ACCOUNT 主体与 `MERCHANT_` 角色，店员的写操作仅限五个订单动作；`/platform/*` 仅平台管理员。前端路由守卫只改善体验，不作为安全边界。商家数据按 `merchant_id` 隔离，学生把订单下到哪个档口，就只能用对应档口的账号接单。

**时间。** 数据库连接强制会话时区 `+08:00`，接口输出带偏移的 ISO-8601 时间字符串，BIGINT 主键序列化为字符串，避免前端解析大整数时精度丢失。

## 5 非功能需求

| 类别 | 要求 |
|---|---|
| 正确性 | 金额恒等式由静态校验器在每次 `check` 时重算；状态 CAS 与库存守卫由真实 MySQL 行为测试逐条断言 |
| 性能 | 菜单接口全天调用最多，靠覆盖索引直查库；订单索引把 `biz_date` 放在合适位置以便后续范围归档 |
| 一致性 | 状态与日志同事务，SSE 推送在事务外；推送失败由兜底扫描补偿 |
| 安全 | JWT 双 token、角色收口、越权查询按归属过滤、密码哈希不落明文、生产配置全部走环境变量 |
| 兼容性 | MySQL 8.0.16 以上，中文排序用 `utf8mb4_unicode_ci`；H5 处理 iOS 安全区、`100dvh` 与键盘遮挡 |
| 可观测 | 统一 `ApiResponse` 带 `traceId`，健康检查暴露库状态，接单台断连可见，全量测试结果写入报告文件 |
| 恢复 | 每 60 秒扫表保证超时任务在进程重启后不丢；数据库定期做完整逻辑备份并验证可恢复 |

## 6 范围边界

**已实现。** 学号登录注册与双 token、档口与菜单管理、服务端购物车、下单与 MOCK 支付、接单出餐核销、SSE 与轮询兜底、支付超时关单、取餐超时完成、自助取消即时退款、商家退款审核、评价与回复字段、收藏地址通知券、报表、平台审核与配置、配送员任务链路。

**未实现或未接真实外部依赖。** CAS 统一身份认证、真实短信网关与频控、学籍认证审核接口、真实支付渠道与异步回调、学生退款申请接口、拒单自动建退款单、部分退款、退款回调幂等、日汇总回写与对账任务、下单与短信限流、埋点、菜单缓存与压测、每日库存初始化。支付回调入口与 `p_callback_log` 已预留，处理顺序写在系统设计说明书里，接渠道时按契约施工。

## 7 上线前置

放量前必须逐项确认：支付开放渠道不是 `MOCK`；下单最低认证状态从内测的 0 改回正式值；所有演示账号删除或改密，控制台占位哈希和统一开发密码清空；短信验证码不再是固定值且双维度限流已上线；JWT 密钥与数据库口令只在环境变量；MySQL 端口不对外暴露；HTTPS 与 HSTS 生效；支付回调验签失败场景实测被拒绝；每个已入驻档口的许可证号与照片已人工核对；备份已实际恢复过一次。完整清单见 `06-测试与验收说明.md` 的验收场景。
