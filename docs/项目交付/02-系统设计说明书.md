# 02 系统设计说明书

## 1 总体架构

```
                 校园网 / 公网
                      │
                 Nginx :443  TLS
                  │         │
        /api →  app :8080    / → 三个前端的构建产物
                  │
        ┌─────────┴─────────┐
     MySQL :3306        进程内定时任务
```

开发期不走容器。后端 8080，学生 H5 5173、桌面 Web 5174、控制台 5175 三个 Vite dev server 把 `/api` 代理到后端。生产按 Docker Compose 起 `nginx`、`app`、`mysql` 三个容器，MySQL 只在内网可达，Redis 等缓存或预扣真正需要时再加。

## 2 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 学生 H5 | Vue 3 + Vite + Vant 4 + Pinia | 扫码即用，覆盖手机浏览器 |
| 学生 Web | Vue 3 + Vite + Pinia，自建设计令牌 | 宽屏双栏，和 H5 共用业务工具 |
| 商家 / 平台控制台 | Vue 3 + Vite，自建组件与 reactive store | 桌面常开，不引 Element Plus |
| 共享包 | `packages/shared`、`packages/api-client` | 金额、时间、字典、ID、请求封装、SSE、营业状态口径 |
| 后端 | Spring Boot 3.2.5 + Java 17 + MyBatis-Plus | 单体，不引 Spring Security |
| 鉴权 | JJWT 双 token | access token 2 小时，refresh token 30 天 |
| 数据库 | MySQL 8.0.16+ | InnoDB，`utf8mb4_unicode_ci`，`DATETIME(3)` |
| 迁移 | Flyway | V1 由 `db/schema.sql` 生成，V2 至 V6 为增量 |
| 实时通道 | SSE | 业务即时推送 + 每 3 秒兜底扫描 |
| 任务调度 | 进程内 `@Scheduled` | 调度池大小 2，单实例运行 |

选择单体而不是微服务依据的是量级。校园全天峰值远低于单个 JVM 的能力，拆服务只会把函数调用变成网络调用。真正的压力在午高峰的菜单读和库存行锁，这两件事在单体里同样能通过索引与事务解决。

## 3 工程结构

```
db/                  数据库真源：schema.sql、seed.sql、tests/
scripts/             校验、迁移生成、样本导入、自动化测试
server/              Spring Boot 后端
  src/main/java/com/campus/smartorder/
    auth cart order payment merchant marketing notify
    review user events console system
    common/          统一响应、错误码、全局异常处理、TraceIdFilter
  src/main/resources/db/migration/   Flyway V1 至 V6
apps/h5  apps/web  apps/console      三个前端应用
packages/shared  packages/api-client  跨端工具与接口层
docs/                设计、契约、接口与交付材料
```

模块之间通过 service 注入调用，禁止跨模块直接查表。响应统一走 `ApiResponse<T>`，结构是 `code`、`message`、`data`、`traceId`，错误码集中在 `common/api/ErrorCode.java`。HTTP 状态码只表达传输结果，业务失败通常为 200 加非零 `code`，鉴权与权限失败分别是 401 和 403。

两条全局序列化约定容易踩坑，也都是真实问题驱动的结果。BIGINT 主键统一序列化为字符串，因为超过 2^53 后前端 `JSON.parse` 会静默改值；时间统一输出带偏移的 ISO-8601，例如 `2026-11-16T12:13:31.727+08:00`，避免同一时刻在不同时区的浏览器上显示不同结果。JDBC 连接串使用数字偏移 `%2B08:00`，不依赖 `mysql.time_zone_name` 导过数据。

## 4 权限模型

控制台权限在 `ConsoleAccess.enforce` 一处判定，前端路由守卫只是体验层。

| 路径 | 主体与角色 | 写权限 |
|---|---|---|
| `/merchant/*` | ACCOUNT + `MERCHANT_` 角色 | 负责人可写；`MERCHANT_STAFF` 只放行 GET 与 accept / start / ready / verify / reject 五个 POST |
| `/platform/*` | ACCOUNT + `PLATFORM_ADMIN` | 平台配置、档口审核、用户管理 |
| `/auth/*`、`/merchants`、`/dishes`、`/orders` 等学生接口 | USER，部分公开 | 订单、地址、券、通知按 `user_id` 过滤 |

同一账号只能看到本店数据，归属校验落在 `merchant_id` 上。学生订单越权查看靠 `user_id` 条件过滤，不靠前端隐藏入口。控制台演示账号使用占位密码哈希，开发期统一密码由 `smartorder.security.dev-account-password` 决定，上线前必须清零并换真实哈希。

## 5 订单状态机与并发

### 5.1 状态转移

| 当前状态 | 可转移到 | 触发者 | 前置条件 | 副作用 |
|---|---|---|---|---|
| `PENDING_PAYMENT` | `PAID` | 支付确认 / 回调 | 验签通过且金额一致 | 分配取餐时段，库存锁定保持 |
| `PENDING_PAYMENT` | `CANCELLED` | 用户 | 未支付 | 释放锁定，还券 |
| `PENDING_PAYMENT` | `CLOSED` | 系统 | 超过 `expire_at` | 释放锁定，还券 |
| `PAID` | `ACCEPTED` | 商家 | 档口营业中 | 计算预计取餐时间 |
| `PAID` | `REJECTED` | 商家 | 必须给原因 | 释放库存；真实渠道接入后建退款单 |
| `PAID` | `REFUNDING` | 用户 | 自助取消窗口内直接退，超窗走审核 | 生成退款单 |
| `ACCEPTED` | `COOKING` | 商家 | — | — |
| `ACCEPTED` / `COOKING` | `READY` | 商家 | 分配取餐码 | 通知用户，锁定转已售 |
| `READY` | `COMPLETED` | 核销或超时 | 取餐码匹配 | 订单结束，计入统计 |
| `REJECTED` | `REFUNDING` | 系统 | 拒单退款 | 生成退款单 |
| `REFUNDING` | `REFUNDED` | 渠道退款成功 | — | 回写净额 |
| `REFUNDING` | 原状态 | 审核驳回 | — | 记日志，不改业务态 |

终态是 `COMPLETED`、`CANCELLED`、`CLOSED`、`REFUNDED`，不接受任何转移。`REJECTED` 和 `CANCELLED` 分开统计，前者计入档口拒单率，后者影响用户信用分。

状态判定集中在 `order/domain/OrderStateMachine.java`，用静态转移表校验合法性并给出这次流转对库存的影响。所有落库动作是把前态写进 `WHERE` 的条件更新，例如：

```java
UPDATE o_order
   SET status = 'ACCEPTED', accepted_at = NOW(3),
       expect_take_at = #{expectTakeAt}, version = version + 1
 WHERE id = #{orderId} AND status = 'PAID'
```

数据库行锁保证同一行上只有一个事务更新成功，其余影响行数为 0，业务层复查当前状态后返回 `ORDER_CONCURRENT_MODIFIED` 或 `ORDER_STATUS_ILLEGAL`。`version` 在状态流转中不是必需，状态本身就是版本；真正用它是改预计取餐时间这类不改变状态的更新。状态变更与日志插入必须在同一事务，日志失败要回滚状态。

### 5.2 下单

```
1  校验用户认证态、档口营业、菜品上架、限购数量
2  价格全部取数据库当前值，忽略客户端传入的金额
3  校验每个必选规格组、选择数范围和加料库存
4  校验券的门槛、档口范围与封顶，事务内核销
5  开事务
6    条件扣减库存
7    写 o_order 与 o_order_item
8    写 o_order_status_log 初始态
9  提交事务
10 事务外清购物车、推 SSE
```

第 10 步必须在事务外，否则回滚后推送已经发出，或者推送失败把下单也拖垮。推送丢失由兜底扫描补上。

### 5.3 防超卖

数据库条件更新是最终防线：

```sql
UPDATE m_dish_stock
   SET stock_locked = stock_locked + 2
 WHERE dish_id = 1 AND biz_date = CURDATE()
   AND stock_total >= stock_locked + stock_sold + 2;
```

影响行数为 0 就是库存不够。规格项的 `stock` 为 `NULL` 表示不限量，非 `NULL` 时同样做条件扣减。Redis 预扣是压测证明有瓶颈之后的二期方案，当前不引入，数据库乐观锁不删除。

### 5.4 支付与回调契约

当前只有 `MOCK` 渠道，前端调用 `POST /payments/{paymentNo}/confirm` 完成支付确认，接口校验支付单归属、幂等、订单是否已关闭，再用两级 CAS 改支付单和订单。没有真实资金，所以「钱收了订单已关」的退款分支无从触发。接真实渠道时按下面顺序施工：

```
1  收到回调，原样写 p_callback_log，含 raw_body、headers、IP、验签结果
2  验签失败记 handled=3，应答 400，不动业务状态
3  按 payment_no 查 p_payment
4  已 SUCCESS 则 handled=2 幂等丢弃，应答 200
5  金额不一致则告警返回失败，不动状态
6  订单已 CLOSED 或 CANCELLED 走自动退款，不改成 PAID
7  CAS 更新支付单 PENDING → SUCCESS，写渠道流水号与 paid_at
8  影响行数为 0 说明并发已处理，幂等成功
9  CAS 置订单 PAID，写取餐计划
10 应答渠道成功格式
```

先落日志再处理是为了任何回调都不丢，进程在处理中崩溃时仍有原始报文可人工补偿。`channel_txn_no` 也参与幂等，因为渠道可能用不同商户单号重发同一笔成功通知。前端轮询支付状态是兜底，和回调调用同一个置为已支付的函数。

### 5.5 定时任务与实时通道

| 频率 | 任务 | 说明 |
|---|---|---|
| 每 60 秒 | 支付超时关单 | 走 `idx_o_timeout (status, expire_at)`，每批 100 条，CAS 关单并释放资源 |
| 每 60 秒 | 取餐超时完成 | `READY` 且 `pickup_deadline_at` 已过，CAS 置 `COMPLETED` |
| 每 3 秒 | SSE 兜底扫描 | 回看 15 秒、限 200 行，与内存上次状态比对去重 |
| 每 20 秒 | SSE 心跳 | 向所有 emitter 发 `ping` |

`GET /events/stream?token=` 按 token 主体决定订阅内容：USER 收个人订单事件 `order`，ACCOUNT 按 `merchantId` 收本店事件 `merchant_order`。事件体只带订单号、档口、状态和服务端时间，前端收到后主动拉详情，不信任事件体。emitter 存活 15 分钟，超时由客户端重连；没有 `Last-Event-ID` 补发，重连后全量重拉。扫表方案在单实例下已经足够，多实例时要给任务加带任务名和批次时间的分布式锁。

## 6 前端设计

三个应用独立构建，只共享类型与工具，不共享运行时。H5 和 Web 共用 `packages/api-client/src/shop/` 下的订单状态到按钮映射、SKU、券、缓存、营业状态和金额工具；H5 的 `utils/` 里对应文件是 re-export。控制台没有 Pinia 和组件库，自建 `UiModal`、`OrderCard` 与一套样式。

状态到动作的映射只维护一份，避免列表能取消而详情不能取消这类不一致。取餐码页用本地缓存先渲染再刷新，食堂信号差时仍能给店员看。倒计时全部按首次响应记录的服务器时间偏移量校正。SSE 断线先指数退避重连，超过次数降级轮询，接单台是 3 秒、学生端是 5 秒。

移动端处理三件具体的事：安全区用 `env(safe-area-inset-*)`，滚动高度用 `100dvh` 并给不支持的浏览器兜底，输入框失焦后手动恢复滚动位置。图片懒加载并固定宽高比占位。

三端都只发真实请求，请求走 `/api/v1`，Vite 把 `/api` 代理到 8080，运行时基址可用 `VITE_API_BASE` 覆盖。模拟层已经移除，接口契约变化时 `packages/api-client` 的类型会直接报错。

## 7 安全与数据口径

密码用 argon2 摘要；开发占位哈希对应的统一密码只在 dev 配置里生效。JWT 密钥、数据库口令、短信密钥在生产配置里全部来自环境变量，代码里不保留环境判断常量。生产配置关闭错误详情与堆栈回显。

数据库是真源，Flyway 只负责运行时升级。`V1__baseline.sql` 由 `scripts/gen-flyway.mjs` 从 `schema.sql` 生成，只保留 `CREATE TABLE IF NOT EXISTS`；`V2` 之后的表结构改动都先查 `information_schema` 再决定是否执行，保证在全新库和老库升级两条路上都能跑。`validate-on-migrate` 保持开启，迁移文件被改动时用 `flyway repair` 或开发库 `start.bat reset` 处理，不通过关校验绕过。

报表口径统一在后端：流水是已支付且非 `CLOSED` / `CANCELLED` 订单的实付之和，净额是流水减已退款；日序列升序补零返回。`st_merchant_daily` 和 `st_dish_daily` 只做历史落表，不是读取源。

## 8 已知边界

多实例部署、Redis 缓存与预扣、延迟队列、对账与日汇总回写、真实渠道回调、限流与埋点都未实现。当前设计的正确性依赖单实例与数据库事务，扩实例之前必须先给定时任务和 SSE 去重加分布式协调。详细的前置条件见 `01-需求规格说明书.md` 的范围边界与 `06-测试与验收说明.md` 的验收场景。
