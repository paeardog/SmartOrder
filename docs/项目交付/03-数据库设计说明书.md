# 03 数据库设计说明书

## 1 概况

数据库真源是 `database/schema.sql`（交付快照，对应仓库的 `db/schema.sql`）。静态校验结果：34 张业务表、450 列、71 个显式二级索引（其中唯一索引 25 个）、23 个外键。初始化脚本 `database/seed.sql` 写入 24 张表共 186 行。

库侧回查 `information_schema` 时是 35 张表，多出来的是 Flyway 的 `flyway_schema_history`；索引口径也不同，库侧把主键和外键自动索引算进去，因此数字比 DDL 统计大，结构本身一致。所有业务表都是 InnoDB、`utf8mb4_unicode_ci`，时间列用 `DATETIME(3)`，金额和数量禁止浮点。

要求 MySQL 8.0.16 及以上。不依赖 `utf8mb4_0900_ai_ci`，MariaDB 10.5+ 也能执行脚本。

## 2 建表约定

**金额用整数分。** 金额列是 `INT UNSIGNED` 或 `BIGINT UNSIGNED`，没有 `FLOAT`、`DOUBLE` 和 `DECIMAL`。浮点加法会产生对不上的尾数，`DECIMAL` 在驱动层会变成字符串或高精度对象。评分同理，商家表 `rating_score` 存 478 表示 4.78。

**订单明细是全量快照。** `o_order_item` 存 `dish_name`、`dish_image`、`category_name`、`option_text`、`unit_price`，档口改名、调价、下架都不影响历史订单还原。`dish_id` 只用于销量回溯。

**对外单号与自增主键分离。** `order_no`、`payment_no`、`refund_no` 是对外标识，`id` 只用于内部关联。暴露自增 ID 既泄露业务量，也让越权遍历变得容易。

**状态变更留痕。** `o_order_status_log` 记录每次流转的前后状态、操作者类型、操作者 ID 和姓名快照、备注与客户端 IP。姓名存快照，三年后员工离职日志仍可读。

**软删除的唯一索引挂 `deleted_flag`。** 有效行是 0，删除时回写自身 id。若挂 `deleted_at`，有效行全是 `NULL`，而 MySQL 唯一索引不约束 `NULL`，重复校验恰好在最需要生效的那一半失效。

**表名按域加前缀。** `sys_` 系统、`u_` 用户、`m_` 商家菜品、`o_` 订单、`p_` 支付、`mk_` 营销、`d_` 配送、`n_` 通知、`st_` 统计。

## 3 分域表清单

| 域 | 表 | 职责 |
|---|---|---|

| 商家菜品 | `m_merchant`、`m_business_hours`、`m_date_override`、`m_menu_category`、`m_dish`、`m_dish_option_group`、`m_dish_option`、`m_dish_stock` | 档口、每周时段、当日覆盖、菜品三层结构、每日库存 |
| 订单 | `o_order`、`o_order_item`、`o_order_status_log`、`o_refund`、`o_review` | 主表、明细快照、流转日志、退款单、评价 |
| 支付 | `p_payment`、`p_callback_log` | 支付流水、渠道回调原始报文；回调日志已预留，真实渠道未接入 |

| 统计 | `st_merchant_daily`、`st_dish_daily` | 按营业日预聚合的历史落表；当前报表从订单表现算，不读这两张表 |

## 4 核心表字段

### 4.1 用户与账号

`u_user` 的登录账号是 `student_no`，`password_hash` 存 argon2 摘要，`auth_source` 区分 CAS、短信、密码和后台导入，`verify_status` 是学籍认证状态，`credit_score` 与 `order_count` 支撑恶意取消和复购统计，`status` 控制封禁。`phone` 与 `student_no` 都可空且有唯一索引，纯统一身份认证用户不需要手机号。

`sys_account` 面向商家和平台，按 `role_code` 区分 `MERCHANT_OWNER`、`MERCHANT_STAFF`、`PLATFORM_ADMIN`，按 `merchant_id` 做数据归属。开发期密码哈希是占位符，统一密码来自环境配置。

`u_auth_token` 保存学生主体的 refresh token 轮换记录；控制台账号与配送员的 refresh token 是无状态 JWT，不落这张表，因为表的外键指向 `u_user`。

### 4.2 档口、菜品与库存

`m_merchant` 存档口名称、分类、招牌与头图、简介、联系人、许可证号与照片、起购金额、打包费、预计出餐分钟、评分和平台状态。`status` 的取值是 0 待审、1 营业、2 打烊、3 封禁、4 驳回。`deleted_at` 是软删除时间。

菜品分三层。`m_dish` 是 SPU，含基础价、单品打包费、限购、供应时段、`stock_mode`、`status` 和 `deleted_flag`。`m_dish_option_group` 用 `group_type` 区分 `SPEC` 互斥单选与 `TOPPING` 多选加价，配合 `required`、`min_select`、`max_select` 描述约束，前端可纯数据驱动渲染。`m_dish_option` 存选项名、加价 `price_delta`（可为负）、是否默认、排序与状态；`stock` 是 `SMALLINT UNSIGNED NULL`，`NULL` 表示不限量，旧版的 `-1` 哨兵会因为扣减后变成 `-2` 而被误判为售罄，已经废弃。

`m_dish_stock` 按 `(dish_id, biz_date)` 存 `stock_total`、`stock_locked`、`stock_sold`，可用量是 `total - locked - sold`。三个数分开是因为「下单未出餐」和「已完成」对库存的影响不同：取消还 `locked`，出餐才转 `sold`。备货按天重置，所以不放一列在 `m_dish` 上。

`m_business_hours` 存每周时段，`m_date_override` 存当日覆盖。覆盖类型有 `CLOSED`、`HOURS`、`OPEN`，`OPEN` 是手动恢复营业写入的当日全天营业记录，次日自动失效。

### 4.3 订单与退款

`o_order` 有 38 列。关键字段：`order_no` 对外单号，`client_order_no` 幂等键，`status` 当前状态，`biz_date` 与 `meal_period` 定位营业日与餐段；金额拆成 `item_amount`、`pack_fee`、`delivery_fee`、`discount_amount`、`pay_amount`；`pickup_code` 在出餐时分配，未分配为 `NULL`；`expire_at` 是支付截止时间，`pickup_deadline_at` 是取餐截止时间；`merchant_name_snapshot`、`pickup_point_name_snapshot`、`dorm_address` 是快照，避免归档后关联不到；`version` 用于不改状态的乐观锁更新。

`o_order_item` 是明细快照，金额恒等式 `line_amount = unit_price × quantity + pack_fee - discount_amount` 由静态校验器逐行重算。`o_order_status_log` 记录每一次流转。`o_refund` 按 `refund_no` 唯一，冗余 `user_id` 与 `merchant_id` 便于两侧待办列表查询，`status` 覆盖 `PENDING` 至 `SUCCEEDED` / `REJECTED`。`o_review` 按 `order_id` 唯一保证一单一评，三项评分、标签、晒图 JSON 与匿名标记都在这张表。

### 4.4 支付、配送与通知

`p_payment` 的 `payment_no` 兼渠道商户订单号，`channel` 是字符串枚举，当前只开 `MOCK`；`status` 为 `PENDING`、`PAYING`、`SUCCESS`、`FAILED`、`CLOSED`；`channel_txn_no` 参与回调幂等。`p_callback_log` 存原始报文、请求头、验签结果、处理状态和耗时，真实渠道接入后每个回调先落这里再处理。

`d_rider` 的 `user_id` 关联学生账号，外键动作是 `ON DELETE SET NULL`，注销账号不删配送历史。`d_delivery` 的 `rider_id` 为空表示待抢单池，`target_building` 是顺路分组键。

`n_notify_message` 保存站内信的已读态、短信外发状态、`retry_count` 与 `last_error`，为短信重发留了位置。`sys_config` 是运行期配置，`PAYMENT_ENABLED_CHANNELS`、`MIN_VERIFY_STATUS_TO_ORDER`、`ORDER_PAY_TIMEOUT_SECONDS` 等都从这里取值。

## 5 索引与约束

`o_order` 的四个业务索引各对应一个高频查询：

| 索引 | 服务的查询 |
|---|---|
| `idx_o_merchant_board (merchant_id, status, biz_date, id)` | 接单台按状态分栏 polling |
| `idx_o_user_list (user_id, biz_date, id)` | 学生订单列表 |
| `idx_o_timeout (status, expire_at)` | 支付超时扫描 |
| `idx_o_pending_board (status, pickup_deadline_at)` | 取餐超时扫描 |

唯一索引 `uk_o_pickup_code (merchant_id, biz_date, pickup_code)` 保证同档口同日取餐码唯一。`uk_o_client_order (user_id, client_order_no)` 兜住重复提交。真实 MySQL 上的 `EXPLAIN` 验证过超时扫描命中 `idx_o_timeout`（range）、接单台命中 `idx_o_merchant_board`（ref，Backward index scan）、核销命中 `uk_o_pickup_code`（const，Using index）。

几处可空列上的唯一索引是有意为之：`u_user.phone`、`u_user.student_no` 允许纯 SSO 用户多行 `NULL`；`d_rider.user_id` 配合 `ON DELETE SET NULL`；`o_order.pickup_code` 在出餐前不参与唯一约束。最初把它写成 `NOT NULL DEFAULT ''` 时，同档口同日第二张待出餐订单会直接撞 `1062`，静态校验和种子数据都没发现这个问题。校验器现在会拦「唯一索引里的字符列是 `NOT NULL DEFAULT ''`」这类写法。

数量列一律 `UNSIGNED`，否则一次重复触发的库存释放能把 `stock_locked` 写成负数且静默污染数据。计算可用量一律写成 `stock_total >= stock_locked + stock_sold + :n`，不写成减法形式，避免无符号下溢把「零行结果」变成 `1690` 异常。

订单主表和两张 `st_*` 汇总表刻意不建外键。订单写入最频繁、留存最久，外键校验在午高峰是可测量的开销；封禁档口或清理毕业生账号也不应被历史订单挡住。引用完整性在下单事务里由应用层校验，靠快照列兜底。

## 6 种子数据与迁移

`database/seed.sql` 给出三个真实档口（川香盖浇饭、兰州牛肉面、悸动奶茶，含规格、加料和限量售罄样例）、一个待审核档口，以及覆盖 `READY`、`PENDING_PAYMENT`、`ACCEPTED`、`COMPLETED`、`CANCELLED` 五种状态的五张订单。控制台账号 `admin`、`chuanxiang`、`chuanxiang02`、`lanzhou`、`jido` 也在种子里。学生口令散列、券模板、持券和地址示例在 `V2` 迁移里，学生演示账号在 `V3`，配送资格在 `V4`。更大规模的样本档口与菜品通过 `pnpm run import:sample` 从 `db/ordering-sample.json` 导入，不属于初始数据。

Flyway 脚本位于 `database/migrations/`，与后端 `server/src/main/resources/db/migration/` 一致：

| 版本 | 内容 |
|---|---|
| V1 | 由 `schema.sql` 生成的建表基线，全部 `CREATE TABLE IF NOT EXISTS` |
| V2 | 学生密码、券模板与地址等结构改动和数据，`information_schema` 守卫保证可重复执行 |
| V3 | 学生端演示账号 `admin`，带 `WHERE NOT EXISTS` 守卫 |
| V4 | 演示配送资格 |
| V5 | 学籍认证备注 |
| V6 | 补齐缺失的菜品与档口图片路径 |

`baseline-on-migrate: true` 与 `baseline-version: 0` 让 Flyway 接受已经手工建过表的库，V1 对它是空操作。`validate-on-migrate` 保持开启；迁移文件改动导致校验和不匹配时，用 `flyway repair` 或在开发库执行 `start.bat reset`，不要关校验。

## 7 校验与执行注意

```
pnpm run check          静态校验 schema.sql 与 seed.sql，不需要数据库
pnpm run check:flyway   比对 schema.sql 生成的基线与仓库中的 V1
pnpm run test:db        在独立的 smartorder_test 库跑 19 个行为测试
```

静态校验检查 SQL 语法、外键指向、列类型、金额与数量列的无符号约束、唯一索引与软删除组合、种子数据的金额恒等式以及 DROP 清单是否覆盖建表清单。行为测试在真实 MySQL 上断言取餐码唯一约束、幂等撞键、外键拦截、状态 CAS 的影响行数、库存条件扣减、无符号越界、`NULL` 语义、JSON 取值、毫秒精度与四个索引的 `EXPLAIN` 结果。两层各抓住过对方抓不到的问题，改库之后都要跑。

`schema.sql` 会 `DROP TABLE IF EXISTS` 全部业务表。它不会删库，但会清空库内数据，只能在空库或明确要重建的开发库执行。`start.bat reset` 的顺序是删 Flyway 历史表、灌 `schema.sql`、灌 `seed.sql`、重放 V1 至 V6，任何一步失败就停下并说明库里缺什么。
