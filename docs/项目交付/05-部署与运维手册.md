# 05 部署与运维手册

## 1 环境要求

开发机是 Windows。后端需要 JDK 17 与 Maven，前端需要 Node.js 22.12 以上和 pnpm 10，数据库需要 MySQL 8.0.16 以上。`start.bat` 会自动把缺少的工具下载进项目根目录的 `.tools/`，已 gitignore，首次运行大约需要下载 470 MB。便携 MySQL 监听 3307，数据文件在 `.tools/mysqldata/`，binlog 已开启。

生产按单机 2 核 4G、40G SSD 起步。Nginx 终结 TLS 并把 `/api` 反代到应用，静态资源由 Nginx 直接提供，MySQL 不对公网暴露端口。生产容器化是规划中的部署方式，仓库里还没有 compose 文件，需要按第 5 节自行编写。

## 2 Windows 一键启动

在项目根目录执行：

```
start.bat            备齐工具链和库，起后端与前端，按任意键收掉这次拉起的服务
start.bat db         只把数据库拉起来并确认有表
start.bat reset      删表重建、重新灌种子数据并重放迁移
start.bat check      静态校验、Flyway 一致性比对、真实 MySQL 行为测试
start.bat build      打成 jar 验证编译链路，不启动服务
start.bat stop       依次收掉后端、前端与便携 MySQL
start.bat help       用法说明
```

工具定位顺序是 `.tools/` 下的目录，再看系统环境。全部缺失时从 Adoptium 或微软取 JDK 17、从 Apache 取 Maven、从 nodejs.org 或镜像取 Node.js、从 MySQL 官网取 8.0.40 便携版，用系统自带的 `curl.exe` 和 `tar.exe` 解压，不需要安装。不想让脚本联网就先设置 `AUTO_INSTALL=0`，它会打印需要手工放置的路径。

便携 MySQL 初始化后监听 `127.0.0.1:3307`，用户 `root`，默认口令 `123456`，可用 `DB_PASS` 覆盖。口令通过 `MYSQL_PWD` 传给客户端，不出现在命令行上；`.tools/my-3307.ini` 的 `[client]` 段也写了口令，手工执行 `mysql --defaults-file=.tools/my-3307.ini` 不用再带参数。后端侧由 `application-dev.yml` 的 `${DB_PASSWORD:123456}` 与脚本导出的 `SPRING_DATASOURCE_PASSWORD` 同时指向这个值。

端口是后端 8080，H5 5173，Web 5174，控制台 5175。后端日志写 `.tools/backend.log`，前端日志写 `.tools/web.log`。端口在给定时间内没起来，脚本会把日志尾部打回当前窗口并如实报告失败。`OPEN_WEB=0` 只开服务不开浏览器，`START_WEB=0` 连前端也不起。

停止分两种。应用窗口还在就按 Ctrl+C，Spring Boot 走优雅关闭，等待最多 20 秒让手头请求处理完；窗口已经关掉就执行 `start.bat stop`，它按端口找进程，先请求退出再强制结束，最后用 `mysqladmin shutdown` 关库。这个命令可以重复执行。`start.bat reset` 会清空所有业务表，执行前确认库里没有需要保留的数据。

## 3 手工建库与启动

已有自己的 MySQL，或不在 Windows 上，按下面的顺序操作。数据库脚本路径相对本交付目录，从仓库根目录执行时写成 `docs/项目交付/database/...`。

```
mysql -u root -p < database/schema.sql
mysql -u root -p smartorder < database/seed.sql
mvn -f server/pom.xml spring-boot:run
pnpm install
pnpm run dev:h5
pnpm run dev:web
pnpm run dev:console
```

`schema.sql` 先 `CREATE DATABASE IF NOT EXISTS smartorder`，再逐表 `DROP TABLE IF EXISTS`。后端启动后 Flyway 在已有结构的库上以基线 0 初始化历史表，接着应用 V1 至 V6。三个 Vite dev server 把 `/api` 代理到 `127.0.0.1:8080`，运行时可以用 `VITE_API_BASE` 覆盖基址。已有服务在跑时不要重复启动，Vite 热更新即可；后端 Java 代码改动必须重启才生效。

## 4 配置说明

| 配置项 | 位置 | 开发默认 | 说明 |
|---|---|---|---|
| 服务端口 | `application.yml` | 8080 | 优雅关闭，等待 20 秒 |
| 数据源 | `application-dev.yml` | `jdbc:mysql://127.0.0.1:3307/smartorder` | 连接串用 `%2B08:00`，不依赖命名时区表 |

| JWT | `application-dev.yml` | 开发密钥 | access 2 小时、refresh 30 天，生产必须换 `${JWT_SECRET}` |
| 开发统一密码 | `application-dev.yml` | `demo123456` | 只对占位哈希生效，上线前清空 |
| 短信 | `application-dev.yml` | 关闭 | 开发桩验证码固定 `000000` |
| 支付渠道 | `application.yml` / `sys_config` | `MOCK` | 生产由 `${PAYMENT_ENABLED_CHANNELS}` 覆盖 |
| 订单时限 | `application.yml` | 支付 10 分钟、取餐 45 分钟、完成 120 分钟 | 每单限 20 件、单品限购 20 |

生产配置在 `application-prod.yml`，数据库地址、账号、口令、JWT 密钥、支付回调地址与短信密钥全部从环境变量读取，代码里没有环境判断常量。生产关闭错误详情与堆栈回显。

## 5 生产部署规划

拓扑见系统设计说明书第 1 节。三个容器的职责：`nginx` 提供 TLS、静态资源和 `/api` 反代；`app` 跑 Spring Boot jar，用 `SPRING_PROFILES_ACTIVE=prod`；`mysql` 挂数据卷，只在 compose 内网可达。上线前需要补齐 compose 文件和 Nginx 配置，把 `DB_HOST`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`、`JWT_SECRET`、`PAYMENT_ENABLED_CHANNELS`、`PAYMENT_CALLBACK_BASE_URL` 等变量接进去。

`db/schema.sql` 只用于初始建库，绝不能在有真实数据的库上执行。已有库用 Flyway 迁移升级，`V1` 对已建结构的库是空操作。数据库升级前先备份并验证可恢复。

## 7 备份与恢复

备份放在项目根目录的 `backups/`，文件名带时间戳，是完整库逻辑转储。Windows 上使用项目自带的 mysqldump：

```
.tools/mysql-8.0.40-winx64/bin/mysqldump.exe ^
  --defaults-file=.tools/my-3307.ini ^
  --single-transaction --routines --triggers --events --hex-blob ^
  --set-gtid-purged=OFF --default-character-set=utf8mb4 ^
  smartorder > backups/smartorder_YYYYMMDD_HHMMSS.sql
```

检查退出码为 0、stderr 为空、文件末尾有 `Dump completed` 行，并核对 `CREATE TABLE` 数量与库中表数一致。恢复时使用同一个客户端：

```
mysql --defaults-file=.tools/my-3307.ini smartorder < backups/smartorder_YYYYMMDD_HHMMSS.sql
```

恢复会覆盖同名表，先在空库或隔离环境验证一次。备份文件包含账号密码哈希、手机号和执照号，仓库即使是私有的也要控制推送范围。生产环境要配置自动备份，并且真的做一次恢复验证，只配任务等于没有备份。

## 8 常见故障

| 现象 | 排查方向 |
|---|---|
| 后端起不来，报 Unknown time zone | 连接串必须是数字偏移 `%2B08:00`，命名时区表未导入时 `Asia/Shanghai` 会失败 |
| 启动报 Flyway checksum mismatch | 迁移文件被改动，用 `flyway repair` 或开发库 `start.bat reset`，不要关校验 |
| 学生全部登录报 `20008` | 库重建后没有重放 V2，学生口令散列没写进去；检查迁移历史与 `u_user.password_hash` |
| 控制台登录失败 | 先确认账号归属与口令，再核对 `dev-account-password` 是否被覆盖、账号是否被停用 |
| 商家看不到新订单 | 确认订单落在哪个档口，用对应档口的账号登录，控制台按 `merchant_id` 隔离 |
| 接单台显示连接已断开 | SSE 断流时会自动降级为 3 秒轮询，横条是刻意保留的显性提示；检查代理是否掐断长连接 |
| 倒计时和服务器时间对不上 | 前端按响应里的 `serverTime` 做偏移校正，检查本机时钟与 `smartorder.zone-id` 配置 |
| 改了 Java 代码没生效 | 后端必须重启；前端是 Vite dev server，热更新即可 |
| 重复执行 `reset` 后表不全 | `schema.sql` 的 DROP 清单必须与 CREATE 清单一一对应，`pnpm run check` 会拦下缺项 |
