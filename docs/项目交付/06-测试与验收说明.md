# 06 测试与验收说明

## 1 测试体系

项目没有 mock 层，三个前端都直连真实后端，所以测试分成静态、数据库行为、单元、类型与构建、服务健康、浏览器和端到端几层。每层抓的问题不一样，缺哪层都会在后面付代价。

| 层次 | 命令 | 覆盖范围 |
|---|---|---|
| 静态校验 | `pnpm run check` | SQL 语法、外键指向、列类型、金额与数量列类型、唯一索引与软删除组合、种子数据金额恒等式、DROP 清单完整性 |
| Flyway 一致性 | `pnpm run check:flyway` | 由 `schema.sql` 重新生成的基线与仓库 V1 逐字节比对 |
| 数据库行为 | `pnpm run test:db` | 真实 MySQL 上 19 个用例：取餐码唯一约束、幂等撞键、外键拦截、状态 CAS 影响行数、库存条件扣减、无符号越界、`NULL` 语义、JSON、毫秒精度、四个 `EXPLAIN` |
| 样本数据 | `pnpm run check:sample` / `test:sample` | 样本档口与菜品导入的自洽性 |
| 前端单测 | `pnpm run test:sku`、`test:platform` 等 | SKU 计算、平台与会话逻辑等六组测试 |
| 后端单测 | Maven 测试 | 状态机、价格、权限、报表口径等服务端逻辑 |
| 类型与构建 | `pnpm run typecheck`、`pnpm run build` | 三个前端与共享包的严格类型检查、生产构建 |
| 服务健康 | `pnpm run test:all` 内含 | 后端与三个前端端口可用，健康接口返回真实库状态 |
| 浏览器自动化 | `pnpm run test:ui` | 本机 Chrome 驱动三端页面，覆盖登录、首页、菜单、收藏、看板，并断言 console 与 pageerror |
| 端到端 | `pnpm run test:all` 内含 | 档口 1 与样本档口真实下单、支付、商家接单；骑手流程需隔离环境 |

一键串联：

```
pnpm run test:all        全部校验与回归
pnpm run test:quick      只跑静态校验、单测和类型检查
pnpm run test:all --no-ui
pnpm run test:ui         单独跑三端浏览器页面检查
```

`test:all` 可用 `--no-db`、`--no-server`、`--no-build`、`--no-ui`、`--no-e2e` 按需跳过。数据库行为测试只重建 `smartorder_test`，不碰开发库 `smartorder`；端到端测试会在真实库留下测试订单。骑手履约测试需要单独的隔离后端，设置 `RIDER_TEST_BASE` 与 `RIDER_TEST_DB` 后才会执行，否则明确跳过。每次运行结果写入 `.tools/test-report.json`，浏览器截图写入 `.tools/ui-*.png`。

## 2 静态与行为两层都要跑

两层各抓到过对方抓不到的真实问题。`pickup_code` 最初写成 `CHAR(6) NOT NULL DEFAULT ''`，静态校验全绿，种子数据也插得进去，因为五张样例订单没踩到；在真实 MySQL 上同档口同日下第二单立刻报 `1062`。反过来，外键指向的列类型是否匹配这类问题，只有静态解析整份 DDL 才能稳定发现。改库之后两层都要过，只跑一层不算验证。

19 个行为测试验证的是语句在 MySQL 里的实际结果，不是纸面推演：唯一约束该拦的必须报错并带指定错误码，状态机 CAS 的影响行数必须是 0 或 1，库存守卫在售罄时返回 0 行，四个热点查询的 `EXPLAIN` 必须命中预期索引。尚未覆盖的是两个事务同时抢同一行库存的真正并发，需要多连接事务脚本或压测证明，数据库条件更新是这一场景的最终防线。

## 4 验收场景

按下面的顺序在真实环境走一遍，每一步都同时验证前端展示和数据库落库。

**学生主链路。** 用种子学生登录 H5 和 Web，切换校区，进入档口菜单，选择规格与加料，加入购物车，进入结算页拿到预校验价格，提交订单，在收银台确认 MOCK 支付，查看订单详情和取餐码。核对 `o_order` 金额、`o_order_item` 明细快照、`p_payment` 状态与 `o_order_status_log` 初始记录。

**商家闭环。** 用订单所属档口的账号登录控制台，看板收到新单并播放提醒，接单、开始制作、出餐，学生端三秒内看到取餐码，店员按码核销。核对状态日志完整、`stock_locked` 在出餐时转为 `stock_sold`、站内信已写入。

**并发冲突。** 两个浏览器窗口同时点接单，必须恰好一个成功，失败方自动刷新状态而不是停在错误提示。同时点改预计取餐时间的场景验证 `version` 乐观锁。

**幂等与价格。** 结算页生成一次 `clientOrderNo`，提交失败后重试复用同一值，最终只有一笔订单。手工在请求体里塞入伪造金额，确认服务端按数据库价格重算。

**超时任务。** 把支付超时配置调成 20 秒，下单不付，观察自动关单并释放库存与券；在关闭瞬间支付应被拒绝。出餐后等待取餐时限，观察自动完成。进程重启后再验证一次，确认扫表任务不丢。

**退款与报表。** 在自助取消窗口内取消订单，核对退款单为 `SUCCEEDED`、库存与券已回退。用负责人账号审核一笔待处理退款，同意后核对净额扣减，驳回后核对订单恢复到退款前状态。商家与平台报表的流水和净额口径与订单表聚合一致，日序列升序补零。

**权限隔离。** 店员账号访问菜单或营业设置应被 403 拦下；学生 A 不能通过改单号看到学生 B 的订单；档口 A 的账号不能操作档口 B 的订单。前端路由守卫隐藏入口不算验证，必须直接发请求。

**通知与评价。** 完成订单后评价，一单一评的限制生效，匿名评价不展示用户身份，档口评价列表按可见态过滤。站内信已读只改自己的记录。

**配送员。** 用具备配送资格的学生账号从 H5 选择配送员登录，查看任务、接单、取餐、送达，核对 `d_delivery` 状态流转。

## 6 测试注意事项

不要为了解决登录失败而执行 `start.bat reset` 或建库脚本，它们会重建数据并清掉已有测试记录。测试操作写入的是真实测试数据库，订单、库存、账号状态与配置的变更会影响其他测试人员，不要修改共享账号密码，不要录入真实隐私信息。支付与退款只在确认的 MOCK 测试环境操作。建议用不同浏览器或独立浏览器配置同时测试不同身份，避免切换账号影响其他会话。
